Data: Creation, Storage and Conversion

1. Creating Datasets

create_sim_data builds Eulerian and Lagrangian datasets of any dimension. The global statistic registry is copied into the dataset, the parameters are copied, and :Solution is coupled to u.

Eulerian (grids)

# 1D + time: u[i, n]
create_sim_data(x, u, t, params)

# 2D + time from axis vectors: u[i, j, n]
create_sim_data((x, y), u, t, params)

# static 3D field with custom axis names
create_sim_data((r, θ, φ), ρ, params; dims = (:r, :θ, :φ))

# ndgrid-style coordinate arrays (x_grid[i, j] == x[i])
create_sim_data((x_grid, y_grid), u, t, params)

The solution may be given as

  • an array of SVectors (M components),
  • an array of numbers (a scalar field, M = 1),
  • an array of numbers with one extra trailing dimension holding the components (u[i, j, n, c]),
  • an array of vectors.

Data is always floating point: integer and rational data is stored as Float64, Float16/Float32 data keeps its type. The typed constructors (DomainInfo{D, T}, ESimData, LSimData) accept only floating-point T. Statistics and spacings are computed in at least Float64 and converted back, so Float16 data doesn't overflow where the result doesn't. The statistics of the presets and check_data are for data of magnitude up to about 1e150: the L2 norms square the values (weighted by the integration measure only afterwards) and the mean sums them, in Float64, so larger values can give Inf. Axes must be sorted. Beyond three spatial dimensions the default axis names are :x1, :x2, …; time is always the last axis (time_dim = :t by default).

xmins, xmaxs, tmin and tmax override the bounding box (e.g. the physical domain [0, 1] of a cell-centred grid). The integration measure (domain.spacing) is always the mean node distance of the axes, independent of these overrides.

Lagrangian (particles)

# x_traj[n][p]::SVector{DS}, u_traj[n][p]::SVector{M} (or numbers), one entry per time step
create_sim_data(x_traj, u_traj, t, params; dims = (:x, :y))

# static particles (no time axis)
create_sim_data(positions, values, params)

Particle counts may differ between time steps. The bounding box defaults to the extent of all positions.

Direct construction

The ESimData/LSimData constructors validate their input (matching axes and solution sizes, consistent dimensions, time as the last axis) and couple :Solution themselves, so derived datasets never need any bookkeeping:

ESimData(params, domain, axes, u)          # DS is inferred from the domain
LSimData(params, domain, t, x, u)

Metadata

Information about a run that isn't data, such as iteration counts, a convergence flag or the provenance, goes into data.metadata (a Dict{Symbol, Any}), not into the statistics: it is saved and loaded with the data but never plotted.

data = create_sim_data(x, u, t, params; metadata = Dict(:iterations => 412, :converged => true))   # e.g. in a solver
data.metadata[:note] = "rerun with the fixed boundary"
save_sim_data(data; overwrite = true)
load_sim_data(params).metadata[:iterations]   # 412

The pipeline writes these entries itself. Their names are reserved: a value of the same name that a solver or you set is replaced, and isn't read as the pipeline's record (a stored :configuration_source that isn't one of the stored source digests counts as unknown).

EntryContent
:provenancehow the data was made: versions of PDEStudioCore and Julia, host, time, number of threads, git commit of the active project (the repository its folder is in, read from .git; uncommitted changes are not recorded), and for pipeline runs the solver (:solver, :solver_module, :solver_version) and the seconds it took (:wall_time)
:sourcesSHA-256 digests of the source files of the run (pipeline runs with sources)
:configuration_sourcethe digest of the configuration's own file, the last of the sources ("" without sources)
:stat_recordsthe records of the statistic layers (see Statistic layers): the digest of the solution and the hash of the parameters they describe, the registered statistics of the data that were evaluated (:simulation), the reference the reference layer was evaluated with and its statistics (:reference; "" for an unknown reference, e.g. from calculate_all_stats!), each with those that came out without a result (all NaN), and for files of earlier versions the statistics a post-processor may have added (:legacy)
:postprocessedthe post-processors that ran on this data (name => the digests of the source files and the package's version, and the statistics it added, :keys), so the pipeline doesn't run them again while they are valid

The metadata saved is the dataset's own: new data replaces the stored metadata (with a new provenance, without :sources and :configuration_source), and an entry of your own that you remove from data.metadata stays removed when you save (the pipeline's entries don't, see next). The statistic records travel with the statistics they describe and are the dataset's own: a dataset without them has none (e.g. a recomputed one: its statistics are evaluated again), and a dataset saved with records of another solution (its data was changed after they were evaluated) or of other parameters (saved under new ones) loses the statistics they describe (for other parameters those of the reference and post-processing layers, which were computed with them), with the records. Writing the same data again (statistics, post-processing, save_sim_data of the stored data, e.g. after add_stat!, or a recomputed dataset) takes the provenance and sources of the stored metadata it doesn't have. Conversions carry the metadata of their source. Metadata is read with every dataset, so keep it small (large results belong into statistics or files of their own).

2. The Statistics View

data.stats returns a StatsView: a dictionary whose :Solution entry is data.u itself.

OperationEffect
data.stats[:Solution]returns data.u
data.stats[:Solution] = v / data.u = vreplaces the solution (size-checked)
delete!(data.stats, :Solution)error: the solution cannot be removed
data.stats[:name] = v, delete!(data.stats, :name)edit derived statistics
keys, values, pairs, haskey, get, lengthas for a Dict, including :Solution
copy(data.stats)plain Dict snapshot

On disk, the solution is stored once (in u).

3. Storage Layout

Every run is one file, <save path>/data/<sha256>.jld2, named by the hash of its normalised parameters (calculate_hash), so a run is found again from its parameters alone. The hash digests a canonical encoding of the parameters in which every value carries its kind and every text its length, so distinct normalised parameters never share an encoding (true and 1, "1" and 1, a matrix and a vector of the same numbers differ; hash format 4, PDEStudioCore 0.8). Normalisation itself is lossy for values that aren't data (see 6.): two values with the same stored text are one run, and generate_tasks refuses a configuration with two such runs. A lookup also checks the parameters stored in the file: a file is only ever taken for, and replaced by, the run its name stands for. A file at the name of a run that holds other parameters, or whose parameters can't be read, is never replaced: saving that run is an error, and the pipeline reports it as failed without running it.

The contract. The store guarantees:

  • data is only ever written to its own name, atomically (see below);
  • nothing moves, renames or deletes data on its own: only delete_sim_data deletes, and only what you ask for (tidy_sim_data removes leftover temporary files);
  • there are no duplicates of a run, so nothing has to choose between copies or clean them up;
  • a rewrite of a file keeps every entry in it (apart from the cached conversions, which belong to the data and go when the data is replaced, and the statistic records of earlier versions, which are written as :stat_records), or fails and leaves the file as it was.

In return it assumes:

  • the files in the data folder are written by PDEStudioCore: your own values belong into metadata, statistics or files of their own (entries you add with JLD2 are kept as far as JLD2 can write them again; otherwise a rewrite fails);
  • the data folder holds no symbolic links: a link at a run's name is never read as the run, written through or replaced;
  • no two processes write the same run at the same time (the last rename wins);
  • the helper files in a configuration's sources are a set: each defines its own names (solvers, references, post-processors, statistics), so the order in which they are included doesn't matter; the file that builds the configuration is the last entry and is included after them (a run records the digests of the files and which one is the configuration's, not the order of the helpers; a file listed twice is refused, also under another path such as a symbolic or hard link). Runs stored before 0.9 don't record which file is the configuration's: for them, a helper that became the configuration file (with the same contents) isn't recognised as changed code; recompute them (force_overwrite = true) if that happened;
  • callbacks (solvers, references, post-processors) don't change a run's parameters: they get copies, and a post-processor that changes them fails; a post-processor adds statistics and metadata and doesn't change the solution or the statistics of the layers above either (it fails, nothing is saved);
  • statistic names are unique across the layers (simulation, reference, post-processing): a registered name that the solver, add_stat! or a post-processor produced is an error; statistic values you change by hand are yours (the records don't track them);
  • only data identifies a run: parameter values are data, or values of custom types that declare what identifies them (param_identity, or @param_struct for types whose fields are all data); functions and undeclared structs are refused. So a struct with functions or derived fields (e.g. a geometric domain's is_interior or volume) is identified by the data its param_identity names, such as its label, bounds and boundary conditions.

Anything outside these assumptions isn't repaired automatically: lookups ignore it, tidy_sim_data lists it, and saves refuse to replace it.

Data of earlier versions (other names) isn't found: PDEStudioCore is in an early stage and keeps no compatibility with them. Recompute it, or copy runs of PDEStudioCore 0.5 to 0.7 (file format 3) into the store with import_sim_data; the old files are only read. Files of PDEStudioCore 0.4 aren't read at all.

Each file contains:

EntryContent
"raw"the native dataset
"native", "params", "stat_keys", "registry", "shape", "dim_keys", "time_dim"fast metadata, read without loading the data ("shape" is size(u), or time steps and total particle count for Lagrangian data; see get_sim_data_info)
"format_version"the layout of the file (see below)
"metadata"the dataset's metadata (stored once, here: "raw" holds the dataset without it), read and updated without loading the data
"evaluated_stats", "evaluated_with_reference", "evaluated_reference"the statistic records of earlier versions: read as :stat_records (the registered statistics in their layers, see Statistic layers), and dropped when the file is written again
"conv_L", "conv_E_<n1>x<n2>…"cached conversions

Other entries (e.g. written with JLD2 directly) are kept when the data is rewritten; if one of them can't be copied, the rewrite fails and the file stays as it was.

The format version is 3 for files written by PDEStudioCore 0.5 and later; import_sim_data refuses files of earlier layouts (0.4).

Writes are atomic: a file is written to a temporary path and renamed into place, so an interrupted run never corrupts existing data, and rewriting the data does not grow the file. This includes the bookkeeping entries of the statistics pass and cached conversions: they are written into a copy of the file that then replaces it (a changed bookkeeping entry grows the file by about its own size, a few hundred bytes to a few kB). When the data itself is rewritten, the other entries are loaded and stored again: load the packages that define the types of entries you stored yourself first, otherwise they are kept as JLD2's reconstructions (with a warning). Writers in several processes are not coordinated: if two of them rewrite the same file at once, the last rename wins. Rewriting the raw data drops stale conversion caches but keeps any other entries (including groups) you stored yourself.

Converted and reference datasets carry the parameters of the native run, so they map to the same file. They are marked as derived (data.metadata[:derived] is :conversion or :reference), and calculate_all_stats! never saves them: neither over the native data nor as the data of parameters that have no file yet (the next run would take the reference for the solver's result). An explicit save_sim_data(...; overwrite = true) of such a dataset does store it, as the native data of its parameters.

4. Loading and Converting

load_sim_data(params)                         # native data
load_sim_data(params, :eulerian, (100, 50))   # grid at spacetime resolution (Nx, Nt)
load_sim_data(params, :lagrangian)            # particles
enable_cache!(true)                           # store conversions in the file
  • Eulerian → Eulerian (resample_eulerian): linear interpolation in space, nearest-neighbour in time (no cross-fading of snapshots); statistics are resampled along the dimensions they keep. Axes whose resolution does not change (e.g. adaptive time steps) are kept as they are.
  • Lagrangian → Eulerian (convert_to_eulerian): inverse-distance scatter of particles and per-particle statistics; empty cells become NaN. Output times take the nearest recorded snapshot. The scatter accumulates in at least Float64 with weights of up to 1e12 (a particle on a node), so values up to about 1e296 in magnitude are converted (values near floatmax aren't supported).
  • Eulerian → Lagrangian (convert_to_lagrangian): grid nodes become stationary particles (sharing one position vector); fields become per-particle statistics.

The resolution res always lists every axis: the spatial resolutions followed by the number of time slices.

5. Managing Data

does_sim_data_exist(params)                         # without loading the data
get_sim_data_info(params)                           # kind, shape, axes and stored time steps, without loading the data
find_sim_data(Dict(:N => 100))                      # list the files of every run with N = 100 (any subset of the parameters)
delete_sim_data(Dict(:scheme => "upwind"); dry_run = true)   # preview, then delete
import_sim_data("old_results/data")                 # copy runs from another folder (other versions, machines) into the store
load_sim_data("a1b2c3"; key = "raw")                # by hash prefix (REPL inspection)
check_data(data)                                    # min/max/mean/NaN summary as a DataFrame
sim_data_table(Dict(:scheme => "upwind"))           # one row per run: file, size, shape, stats, solver, wall time, parameters
tidy_sim_data(dry_run = true)                       # leftovers of killed writes, and files that aren't part of the store

find_sim_data prints one line per matching run (most recently written first) with the remaining parameters and returns the paths; delete_sim_data deletes exactly the files it would list and refuses an empty filter. sim_data_table reads only the metadata of each file, so it is quick for large data folders. These three only see the store: files at their own name. Their filters compare values as the hash tells them apart: Dict(:k => 1) matches neither true nor 1.0.

import_sim_data copies runs from a file or folder (recursively) outside the data folder into the store, each to its name; it only reads its source, and a run that is stored already is skipped, so an interrupted import is simply run again. Each source file is copied next to its destination and that copy is checked before it is renamed into place: it must hold a dataset whose parameters, kind and shape are those stored in the file. Nothing at a destination is replaced: a stored file of the same parameters that isn't a usable run (e.g. without its dataset), a file of other parameters and a symbolic link are reported; move or delete them, then import again. remove_keys drops parameters that didn't affect the result (e.g. one that no longer exists); the run is copied as it is otherwise, with its statistics and records. To change a parameter that matters, run the solver again. To drop a key from runs already in the store, move their files out of the data folder and import them back with remove_keys.

tidy_sim_data removes temporary files of writes that never finished (older than an hour by default) and lists the files in the data folder that lookups don't use: other names (e.g. of earlier versions), parameters with another hash than the name, parameters that can't be read or aren't valid parameters of this version (e.g. written by an earlier one), and symbolic links. Listings and deletions only see files at their own name and skip the others; an import checks the contents of its source files whatever they are named, and skips (and reports) one whose parameters aren't valid. It never deletes them: move them out of the data folder, import what you need, and delete the rest yourself.

A lookup is a single path, so files added or removed by other processes are seen at once. Parallel jobs computing the same parameters write the same file; the last rename wins.

6. Parameter Normalisation

Before hashing and saving, parameters are normalised: functions are refused, custom structs become a descriptive string from what identifies them (their type name and their param_identity: TypeName(key=value, …); a struct whose identity is empty, such as the tag Limiter{:minmod}(), by its type with its parameters; type names are written without module prefixes, so the text doesn't depend on what the session loaded with using) and other values round-trip through val2str/str2val. Strings are always kept verbatim, so a parameter such as :ic => "sin" stays a string. str2val only parses literals (numbers, strings, symbols, tuples, vectors, Dicts, static arrays, arithmetic like 2π and a range as the whole value, e.g. a sweep typed as 1:10); it never executes code. Types come from an allowlist (numbers, text, the containers val2str writes and StaticArrays), and what a value may build is bounded (elements, digits, the size of types including static arrays, nesting), so a file cannot run code, and these limits bound what the parser computes and compiles for a text; anything else is kept as a string. Inspect the stored form with print_clean_params.

What identifies a parameter value. Two values are the same parameter (and so the same run, if all others agree) exactly when their stored forms are equal. The rules, fixed since hash format 4 and pinned by a test corpus (test/test_store.jl), so they don't change silently:

  • numbers by type and value; the numbers of parameters are Int64, Float64 and Bool (Float32 and Float16 are stored as Float64), any other number is refused (other integer widths, BigInt, rationals, complex numbers, your own number types): convert it for the parameters (e.g. Int64(x)), also if the solver uses another type; true is not 1, 1 is not 1.0. A Float32 or Float16 is stored as the Float64 of its shortest decimal text (0.1f0 as 0.1, not as Float64(0.1f0));
  • strings by their text (any string type), symbols, characters (Char; other character types are refused), nothing and missing as such, but only as a parameter value of their own: inside a container or an identity they are refused (they would be written as the types Nothing/Missing, which are values too; use a Symbol such as :none, or the type); a string or enum type of your own that declares a param_identity is refused (it would be stored by its text or name);
  • tuples, pairs, vectors, arrays (with their shape), static arrays and Dicts by their element type and elements. An array is identified by its element type, shape and elements, not by its array type: a range, a static vector, a BitVector or a view is the same value as the Vector (or Array) with its elements, as isequal says (named tuples are refused: use a Dict, or a type with a declared identity; sets are refused: use a sorted vector or a tuple). The keys of a Dict are all of one type: Symbol (a ParamDict), String or Int64; a Dict is stored with its keys in the order of their text;
  • types (as values, as element types, in Val{…}) by their name only, without the module they come from: Base.Matrix and a Matrix of your own are the same value, and a session stores and finds them alike whatever it loaded with using. A type is written as text, so the values among its parameters are Symbols, Chars, Int64, Bool, floats or nothing (Val{1}, Limiter{:minmod}, SVector{3, Float64}); other values are refused (Val{Int32(1)} prints like Val{1}), and so is NaN (NaNs with other bits are other types, all written NaN);
  • values of custom types by their type name and what their param_identity names (its field names must be plain identifiers; all stored fields with @param_struct); a type that doesn't declare it is refused. Such a value is stored as its text (TypeName(field=…)), and so are enum values (TypeName.value) and containers holding one of them: a string with exactly that text is the same parameter, on purpose (configuration files, e.g. PDEStudio's CSV files, give such values as text). A solver gets one or the other and has to treat them alike. A param_identity must be a pure function of the value. An empty identity counts the type parameters (e.g. Limiter{:minmod});
  • functions are refused: what a function computes can't be compared. Name it (:ic => "sin", looked up in the solver), or keep it in a struct whose param_identity leaves it out and names what tells such values apart (e.g. a geometric domain: its label, bounds, boundary conditions and shape, not its is_interior, get_tag, volume or piece_of_tag).

So don't use values that differ only in what these rules leave out (what a param_identity leaves out, the module of a type, the type parameters of a struct with a non-empty identity, Float32 against Float64, the array type, a value stored as text against that text) to tell runs apart: a configuration with two such runs is refused, and across configurations they are one run.
