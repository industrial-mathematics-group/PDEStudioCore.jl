The previous two destructive overwrites are fixed. Cleanup now groups files by their stored parameters, but it can retain an unusable partial copy and permanently delete the complete simulation. Four additional cases concern the new staging and link handling in rehash.

## Findings in this release

1. **Critical — cleanup deletes the only solution.** At `src/DataManagement.jl:359` and line 365, readable parameters qualify a file for duplicate removal and modification time selects the survivor. I copied a valid field of 7 to a filename with a different hash, removed only its JLD2 `raw` entry and made the complete file older. Default `tidy_sim_data()` deleted the complete file. The remaining file had no solution, and `does_sim_data_exist(q)` was false. On 0.7.0 the identical input preserved the complete, loadable run. Before deleting any copy, verify that a survivor under a discoverable filename can load the expected native solution. Leave ambiguous groups untouched.
2. **Major — a filtered rehash deletes an unrelated symlink.** At `src/DataManagement.jl:183` and line 280, links are selected before applying parameter filters and removed after the batch. A link and its target had `:k => "run"`. Calling `rehash_sim_data(; filter_pairs=Dict(:k=>"unmatched"))` removed the link, even though no target matched or moved. Version 0.7.0 preserved it. Remove links only for selected targets successfully moved away from their old names.
3. **Major — recovery moves unrelated files during a single-file rehash.** At `src/DataManagement.jl:295` and line 303, any directory starting with `.rehash-` qualifies as a recovery directory and all of its contents are moved up. Calling `rehash_sim_data(file)` on an already correctly named run relocated `.rehash-backup/notes.txt` into the data directory and removed its original directory. Version 0.7.0 left the notes in place. Verify staging ownership with a manifest of paths before moving anything.
4. **Major — crash recovery misses a fully staged directory.** At `src/DataManagement.jl:177`, recovery searches the parents of the discovered JLD2 files. I modeled interruption after the sole run was moved to `data/.rehash-0/`. Retrying `rehash_sim_data()` inspected the staging directory for children, skipped its parent and left the run invisible. The added regression test leaves a second file in the parent, so it misses this state. Discover staging directories starting at the requested root, restore them first, then enumerate the resulting files. Version 0.7.0 also failed this input, but 0.7.1 introduces this recovery mechanism and promises recovery on retry.
5. **Major — rewriting an external relative symlink fails after staging.** At `src/DataManagement.jl:238` and line 261, moving a relative link into a subdirectory changes how its target resolves. A link to `../shared.jld2` passed to `rehash_sim_data(; remove_keys=[:obsolete])` produced zero rewrites and no result under the requested parameters. On 0.7.0 the same case produced one usable result. Both versions preserved the external target. Resolve the input relative to the original link location when preparing the rewrite.
