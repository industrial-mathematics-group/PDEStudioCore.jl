## Findings

### 1. Low — CONFIRMED — `_reconstructed_type` misses untyped containers inside concretely typed ones, and the values of large Dicts
- **Where:** `src/IOUtils.jl:190-192`.
  - A container is entered only when its own `eltype` (or `keytype`/`valtype`) is not concrete.
  - For Dicts, `Iterators.flatten((keys(value), values(value)))` visits every key before any value, under a cap of 10^4 items.
- **What:**
  - `Vector{Any}` and `Dict{Symbol, Any}` are themselves concrete types, so a container whose element type is one of them is never entered: `Vector{Vector{Any}}`, `Dict{String, Dict{Symbol, Any}}`, `Dict{Symbol, Vector{Any}}`.
  - NamedTuples, Pairs and Sets are not entered either.
  - In a `Dict{Symbol, Any}` with 10^4 or more entries, the keys use up the cap and no value is inspected. That is the shape the commit message names ("Dict{Symbol, Any}").
- **Scenario:**
  - User metadata such as `Dict("run" => Dict{Symbol, Any}(:solver => SomeType))`, or a list of per-run `Any` vectors (`[Any[…], …]`).
  - The next rewrite of the data (`save_sim_data(…; overwrite = true)`, post-processing, rehash) stores them back as JLD2 reconstructions with no PDEStudioCore warning.
  - Only JLD2's generic "reconstructing" line appears, which is what the earlier minor was about.
- **Evidence:** `probes/probe_reconstructed.out`, section "false negatives": 9 of 10 variants return `nothing`. End to end, the overwrite warns only for `"top"` (a `Dict{Symbol, Any}`). `"nested"` (`Dict{String, Dict{Symbol, Any}}`) and `"vv"` (`Vector{Vector{Any}}`) get no warning.
- **Fix:** also enter a container whose element type is a container type that can hold abstract elements. This can be checked statically and cheaply:
  ```julia
  _may_hide(T) = T isa Type && (!isconcretetype(T) || (T <: Union{AbstractArray, AbstractDict, Tuple, NamedTuple, Pair} &&
                 any(_may_hide, T <: AbstractDict ? (keytype(T), valtype(T)) : (eltype(T),))))
  ```
  - Use `_may_hide(eltype(value))` instead of `!isconcretetype(eltype(value))`, and bound the recursion of `_may_hide` itself.
  - Iterate Dicts by pairs (`k, v` together), so large Dicts still get their values checked.
  - Also enter `NamedTuple` and `Pair` values.
- **Test:** add these to the `for k in (…)` loop in `test/test_data.jl:119-123`:
  - `[Any[H]]`
  - `Dict("a" => Dict{Symbol, Any}(:h => anon.Hidden))`
  - a `Dict{Symbol, Any}` with 10^4 + 1 entries, one of whose values is `anon.Hidden`

### 2. Low — CONFIRMED — The cost bound is per container, not per entry: nested untyped data can take seconds and GiBs on every rewrite
- **Where:** `src/IOUtils.jl:185-199`: `i > 10^4 && break` caps each container, and `depth = 4`. The check runs in `_copy_entry!` for every carried-over entry, on every rewrite of the data.
- **What:**
  - The comment says "nested containers up to a depth of 4, at most 10^4 elements each are inspected". That is true, but it allows up to 10^4 + 10^8 + 10^12 + 10^16 visits; in practice the limit is the size of the data.
  - Each visit allocates (`string(T)`), at about 250 B–2.6 KB per element, and deeper nesting costs more per element.
- **Scenario:** a user entry that is a nested `Any` structure with 10^6 leaves, such as a per-step history `Any[Any[Any[…]]]`. Every `save_sim_data(…; overwrite = true)`, `post_func` rewrite and rehash of that file then spends seconds and GiBs of allocation on the check alone.
- **Evidence:** `probes/probe_cost_nested.out`:
  - 8.1·10^5 leaves at depth 4: 4.9 s, 2.0 GiB
  - 10^6 leaves at depth 3: 1.97 s, 885 MiB
  - 10^6 leaves at depth 2: 0.40 s, 253 MiB
  - Flat input is cheap: 10^6- and 10^7-element vectors take 2 ms (`probes/probe_reconstructed.out`).
- **Fix:**
  - Share one budget across the whole recursion, e.g. a `Ref{Int}` counter of 10^4 visits per entry, so the total cost is constant.
  - Optionally, detect the markers on the type itself (walk `T.parameters` / check `T.name.module === JLD2`) instead of `string(T)`, which avoids the allocation.
  - Update the comment.
- **Test:** `@test @elapsed(PDEStudioCore._reconstructed_type(Any[Any[Any[Any[0.0 for _ in 1:30] for _ in 1:30] for _ in 1:30] for _ in 1:30])) < 0.5` (it takes 4.9 s now).

### 3. Low — CONFIRMED — The new reserved names `"dim_keys"`/`"time_dim"`: user metadata of old files is trusted and then silently dropped, and the API change isn't documented
- **Where:**
  - `src/IOUtils.jl:18` (`_MANAGED_KEYS`)
  - `src/IOUtils.jl:349`: `get_sim_data_info` trusts any entries with these names
  - the storage-layout table in `docs/src/data.md:72-80`
- **What:** before this commit, `save_sim_data(…; metadata = Dict("dim_keys" => …, "time_dim" => …))` was accepted and stored as user entries. Now:
  - **(a)** that call throws `ArgumentError: metadata key 'time_dim' is reserved`. This is a small public API change, and neither the commit nor the docs mention it.
  - **(b)** for an existing file with those user entries, `get_sim_data_info` returns them as the axes and even computes `n_steps` from them (`dim_keys = ("user",)`, `time_dim = "user value"`, `n_steps = 2`).
  - **(c)** the next rewrite treats them as managed entries and replaces them without a warning. `data.md` still promises that "Rewriting the raw data … keeps any other entries … you stored yourself".
  - The storage table in `data.md` doesn't list the new entries, so users can't know these names are taken.
- **Scenario:** unlikely, because the names are specific. It needs a user who stored their own `"time_dim"` metadata with an earlier version.
- **Evidence:** `probes/probe_info.out`, sections "reserved metadata keys" and "an old file whose user metadata …" (the old file was written by 6e36904).
- **Fix:**
  - Add `"dim_keys"`, `"time_dim"` to the `data.md` table, as fast metadata, noting that files written before this change have none.
  - In `get_sim_data_info`, accept the stored entries only if `dim_keys` is a `Vector{Symbol}`, `time_dim isa Union{Nothing, Symbol}`, and, for Eulerian data, `length(dim_keys) == length(shape)`. Otherwise use the fallback.
  - Mention the newly reserved names in the PR description.
- **Test:** write a file without the entries but with a user `"time_dim" => "x"`, and check that `get_sim_data_info` still returns the data's axes. The stripping loop of the new test already does most of this.

## Minor issues

- **`get_sim_data_info` docstring** (`src/IOUtils.jl:335-344`):
  - It throws `ArgumentError`, not `SimFileNotFoundError`, for files without `"native"`/`"shape"`. The docstring should say so.
  - "the data is loaded once to read them" really means once per call. The result is never written back, so PDEStudio pays a full raw load for every call on an older file (7.9 MiB on each of three calls, `probes/probe_info_cost.out`). Either say "on every call", or write the two entries back with `_update_entries!(path, …; only_missing = true)`, which is atomic and adds about 1 kB.
- **`get_sim_data_info` opens the file twice** (`_native_and_shape`, then `"dim_keys"`/`"time_dim"`). A concurrent `save_sim_data(…; overwrite = true)` that renames a new file in between could pair the old shape with the new axes. SUSPECTED, not reproduced. Read all four entries in one `jldopen`.
- **`_RECONSTRUCTED` is not anchored** (pre-existing and contrived): a user module whose name ends in `JLD2` (`Main.MyJLD2.Reconstructed`) matches (`probes/probe_reconstructed.out`). `r"(?<![\w.])JLD2\.(Reconstructed|Serialized|UnknownType)"` would fix it.
- **Rehash of a directory that contains both a link and its target** (`probes/probe_symlink.out`, "dedup"):
  - The warning says the target "is kept", but the same walk then rehashes and deletes the target.
  - The result is two files under the new hash, with the same data; the newest wins.
  - Harmless, but the message is wrong in this case. "is not deleted by this rehash of the link" would be accurate.
- **Collision with an existing symlink** (pre-existing, but related to the rationale of this change):
  - If the new name of a rehashed file is an existing symlink, `_write_sim_file` writes through it and overwrites the shared target (`probes/probe_symlink.out`, "collision": `u` 7.0 → 1.0).
  - The only warning is "already exists and is replaced".
  - This is consistent with "a symlinked data file stays a symlink, and its target is updated", but it is the one rehash path that still changes a target that may be shared.
- **`docs/src/data.md:76`:** the storage-layout table lacks `"dim_keys"`/`"time_dim"` (part of Finding 3). The `IOUtils.jl` header comment is accurate.

## Verdict

`get_sim_data_info` is correct. It returns the right kind, shape, axes and `n_steps` for every data kind and layout I tried. That includes files written by the previous code, and files after bookkeeping, overwrites, layout changes and rehashes.

- Every path that writes `"raw"` writes the new entries.
- Both names are managed, so nothing stale survives a rewrite.
- Hashes are untouched.
- The atomic-write design is kept: the entries are written into `_write_sim_file`'s temporary file.

The symlink warning is accurate and appears exactly when a link is removed.

The broadened reconstruction check has no false positives on ordinary values and names the missing type. Its weak spots:
- It still misses `Any` containers nested in concretely typed ones, and the values of large Dicts (Finding 1).
- Its cost is bounded per container rather than per entry (Finding 2).

The new reserved names trust, and then silently drop, user metadata with the same names in older files (Finding 3, unlikely in practice).

The suite passes (448/448), the docs build with `checkdocs = :exports`, and the new tests fail on the old code where they should.

Findings: 0 high, 0 medium, 3 low (1, 2, 3).
