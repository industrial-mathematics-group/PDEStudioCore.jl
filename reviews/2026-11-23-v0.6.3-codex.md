## Summary

All 1,440 tests passed, including the regression cases covering the 13 findings in the previous review. I reproduced three regressions relative to 0.6.2. Two lose stored information during ordinary saves or statistics updates, and one produces incorrect particle-to-grid values. The previous release reproduced six additional issues still present at the reviewed head.

## Findings introduced by the fix

1. **Critical — saving one string parameter overwrites a different run.** At `src/Serialization.jl:451`, the single-character string `1` is encoded with quotes for hashing. A three-character string consisting of a double quote, the digit 1 and a double quote is emitted verbatim. Both now have identical hash input. A sweep with these two string values shrank from two tasks in 0.6.2 to one. In a fresh store I saved field 20 for the quoted value, then field 10 for the other with `overwrite=true`. The quoted value subsequently loaded as 10 and there was only one file. On 0.6.2 the same calls preserved both files and the field 20. Use an unambiguous versioned encoding of normalized parameter keys and values. Guard replacement by checking parameter identity, including compatible old names. See `fresh_hash_case`.
2. **Critical — a statistics update erases user metadata from an older file.** At `src/IOUtils.jl:26` and `src/IOUtils.jl:493`, the new bookkeeping name `evaluated_reference` is treated as reserved even in file formats where users owned that name. On a copy of the shipped 0.4 fixture, I added the user entry `"laboratory calibration"`. Version 0.6.2 exposed it through `data.metadata` and preserved it through upgrade and statistics calculation. Version 0.6.3 hid it immediately. After the same upgrade and calculation the metadata lacked the key and the top-level entry contained the empty string. Distinguish bookkeeping by format or namespace and migrate the old user value into metadata before writing the new record. See `legacy_metadata_case`.
3. **Major — Float16 scatter can turn a spatially varying field into a constant.** At `src/ConversionUtils.jl:50` and `src/ConversionUtils.jl:68`, the squared smoothing radius is computed in Float16 before conversion to the wider accumulator. For particles at 1 and 255 with states 1 and 3, scattering onto nodes 0 and 256 makes the radius squared infinite. Both particles receive equal weights at both nodes. The result was `[2, 2]` on the reviewed head and `[1, 3]` on 0.6.2. Compute the coordinate differences, spacing, squared distances and squared radius in a wider type before normalizing. Test scale changes as well as exact node hits. See `scatter_case`.
