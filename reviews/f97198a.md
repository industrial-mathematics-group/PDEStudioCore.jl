## Findings

### 1. Medium — CONFIRMED — The power bound can be bypassed by `Int` overflow in `abs(values[2]) * _exact_bits(values[1])`
- Where: `src/Serialization.jl:135`.
- What: the product is computed in `Int`. For an `Int` exponent ≥ 2^62 and a 2-bit base it wraps to a negative number
  (`2^62 * 2 == typemin(Int)`), and for suitable exponents to a small positive one (`6148914691236517206 * 3 == 2`). The check
  `> _MAX_LITERAL_BITS` then passes. (`abs(typemin(Int))` is negative too, but that only reaches a `DomainError`.)
- Scenario: a CSV/GUI value `(BigInt(3)//1)^(2^62)` or `(BigInt(3)+0im)^(2^62)` is passed to `str2val`.
  `power_by_squaring` squares until memory runs out. With `ulimit -v 4 GB` this took 16–18 s. The `Rational` case left the
  heap corrupted, and the process aborted (SIGABRT, "corrupted double-linked list", core dump). Without a ulimit it grows to the
  container's 32 GB limit. A plain `BigInt(3)^(2^62)` is safe only because GMP fails fast.
- Evidence: `psc/probe_literals.out` ("overflow in the size product": `2^62 * bits = typemin`, check `false`),
  `psc/probe_overflow.out`.
- Fix: compute the bound without overflow, e.g.
  `b = _exact_bits(values[1]); b > 0 && abs(big(values[2])) > _MAX_LITERAL_BITS ÷ b && throw(_NotALiteral())`
  (or use `Base.checked_mul` and treat `OverflowError` as too large). Add `str2val("(BigInt(3)//1)^(2^62)") isa String`
  to the tests. It returns quickly once the check is right.

### 2. Low/Medium — CONFIRMED — The range cap is per range: N7 still holds for containers of ranges
- Where: `src/Serialization.jl:138` (only the single `(:)` result is bounded). Hashing is done by `val2str` in `src/Serialization.jl:31-36`.
- What: `(1:10^6, 1:10^6, …)` or `Any[1:10^6, …]` passes the cap for each element. Every element costs 10^6 written-out values
  in every hash (each lookup and save). The amplification is about 10^5 values per input character.
- Scenario: a 160-character value with 20 ranges took 7.0 s to `_param_hash`. By extrapolation, about 1 KB of input
  (~140 ranges) takes about a minute and several GB of string. About 10 KB of input runs the process out of memory.
- Evidence: `psc/probe_literals.out` (testset "tuple of ranges").
- Fix: a total element budget per `str2val` call (for example a counter threaded through `_literal`, or a task-local one),
  or bound the total length of all ranges in the result. Alternatively, cap ranges far lower: parameters with 10^6-element ranges
  are not practical anyway, because each hash costs 0.65 s.

### 3. Low/Medium — CONFIRMED — N3 is only fixed for entry updates: a stats pass that computes statistics still degrades user entries of unloaded types
- Where: `src/StatCalculation.jl:256` → `_save_sim_data(…, changed, …)` → `src/IOUtils.jl:188-215` (`_write_sim_file`
  carries over old entries by load + store, `_copy_entry!`).
- What: the byte-copy `_update_entries!` fixes the conversion-cache path and the bookkeeping-only path (verified). But
  whenever statistics are computed (the normal case for a fresh file in `run_all_simulations(…; calculate_stats = true)`),
  post-processing returns `true`, or there is an explicit overwrite, the file is rebuilt and user entries are loaded and stored again.
  In a session that lacks the user's type (pipeline on a cluster, a GUI session), JLD2 reconstructs the type and writes back
  `JLD2.ReconstructedStatic{…}` permanently. It only logs a JLD2 "reconstructing" warning, with no warning from this package.
  `docs/src/data.md:82` still promises that other entries "you stored yourself" are kept.
- Scenario: process A saves data with `metadata = Dict("note" => UserNote(3))`. Process B, without `UserNote`, runs
  `calculate_all_stats!(load_sim_data(p))` with the hyperbolic preset. In process C, which defines `UserNote`, the note is
  now `JLD2.ReconstructedStatic{:UserNote, (:a,), Tuple{Int64}}`.
- Evidence: `psc/probe_copy.out`, case "A=plain B=stats". The cases "A=plain B=cache" and "A=withstats B=stats" now keep the type.
- Fix: in `_write_sim_file`, skip (with a warning) carried-over entries whose loaded value is a `JLD2.Reconstructed*` type or
  contains one. Or skip the load entirely for carried-over entries: byte-copy the old file, then `delete!` and rewrite only the
  managed entries and `conv_*`. That grows the file by the data size per rewrite, so prefer the skip, or document the limitation in `data.md`.

### 4. Low — CONFIRMED — Symlinked data file: the update modifies the target in place, then throws
- Where: `src/IOUtils.jl:140-147` (`cp(path, tmp)` with the default `follow_symlinks = false`).
- What: if `data/<…>.jld2` is a symlink, `cp` copies the link itself. `jldopen(tmp, "a+")` then writes into the real file
  in place, so the write is not atomic, and `mv(tmp, path)` throws `ArgumentError: 'src' and 'dst' refer to the same file`.
  Every stats bookkeeping update or cache write on such a file throws, and the stats task is logged as failed, although the
  entry has already been written into the target. The old code (and `_write_sim_file`) replaced the link with a regular file and worked.
- Evidence: `psc/probe_update.out` ("symlinked data file": update throws, `flag in target = true`, no `.tmp` left).
- Fix: `cp(path, tmp; follow_symlinks = true)`. The rename then replaces the link with a regular file, like the other writers.
  Data directories with symlinked files are probably rare, hence low severity.

### 5. Low — CONFIRMED — Growth claim understates it for `evaluated_stats`
- Where: `docs/src/data.md:82` ("a changed bookkeeping entry grows the file by a few hundred bytes"), comment at
  `src/IOUtils.jl:128-132`; test bound `test/test_data.jl:97` (`size0 + 4096`, Bool flag only).
- What: a changed Bool flag adds 138 B. A changed `evaluated_stats` (`Vector{Symbol}`) adds about 4.3 KB each time, and the first
  write of both bookkeeping entries about 4.4 KB. JLD2 in `"a+"` appears to commit the datatype again on each write.
  This is harmless in size (the entry changes only when the registry changes), but the docs say "a few hundred bytes".
- Evidence: `psc/probe_update.out` (`diffs: [4407, 138 ×20, 4282, 4296, 4312, 4328, 4344]`).
- Fix: say "a few KB", or "grows by the size of the changed entry (a few KB at most)".

## Minor issues

- `src/Serialization.jl:125`: `_exact_bits(::Integer)` also counts fixed-size integers, and `_exact_bits(::Rational)` counts
  `Rational{Int}`. So `2^(10^6)`, `im^(10^7)` and `(1//2)^(10^6)` are now returned as strings. These are overflowed or
  overflowing values nobody uses. Harmless, but the comment "fixed-size results → 0" suggests otherwise.
  Restricting the check to `BigInt`-based types would match the intent.
- `0:1e-6:1.5` (1.5·10^6 elements) is now rejected. That is reasonable, but it is a behaviour change for user-typed ranges.
  It isn't mentioned in the `str2val` docstring.
- Pre-existing and out of scope (already reported in `reviews/efe7700.md`): `Float32` values don't round-trip through `val2str` (`0.001f0 → 0.001`).

## Verdict

Most of the fix set is correct. The Bool sweep fix, the RNG-free temp names, the byte-copy entry updates (cache and bookkeeping
paths keep user entries now) and the new docs are accurate, apart from Finding 5. All values that round-trip today still
round-trip. The size bounds are the weak spot: the power bound is bypassed by `Int` overflow, which still crashes a process from
a short literal (Finding 1, medium). The range cap is per range, so a tuple of ranges still makes hashing take minutes (Finding 2).
N3 is fixed for entry updates but not for data rewrites in a session that lacks the user's type (Finding 3). The suite passes (415/415).
