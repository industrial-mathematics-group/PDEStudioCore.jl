## Findings introduced by #72

1. **Major. L2 can report zero for an undefined component or reference comparison.** `src/StatCalculation.jl:99–116` ignores NaNs while finding the maximum magnitude, then unconditionally returns zero when that maximum is zero. With a two-component field whose first component was `[0, NaN]`, #72 returned `[0, √5]` and the first parent returned `[NaN, √5]`. With a finite scalar field and a reference that matched at one node and was undefined at the other, #72 stored L2 error `[0]`. The first parent omitted the all-NaN error, consistent with the public missing-value policy. Preserve NaN propagation and distinguish truly all-zero data from zeros mixed with missing values. [L2 fallback](../src/StatCalculation.jl#L95) · [Current output](2026-11-26-main-89be634-codex-evidence/l2-edges-head.txt) · [First parent](2026-11-26-main-89be634-codex-evidence/l2-edges-base.txt)
2. **Minor. A metadata-only save can rerun an unchanged pre-#72 post-processor.** The fingerprint now includes a representation tag at `src/StatLayers.jl:175–179`. A normal save writes the new upstream fingerprint through `src/IOUtils.jl:358`, while the callback's existing record keeps its old fingerprint. I upgraded a #70 file with one completed metadata-only callback. With the same sources and upstream statistics, it first reported `:skipped`. I saved an unrelated note, and it then reported `:ran`, incrementing its stored invocation count to 2. The same save on the first parent leaves the count at 1. Version the fingerprint or migrate equivalent old records when rewriting them. [Fingerprint](../src/StatLayers.jl#L171) · [Cache check](../src/Simulations.jl#L480) · [Upgrade outputs](2026-11-26-main-89be634-codex-evidence/README.md)

## Existing findings in the whole-codebase snapshot

1. **Critical, residual #70 ownership issue. A file already saved with an incorrect owner can still lose its solver statistic.** Removing the write tracker prevents new incorrect ownership records. I prepared a 0.9 run, ran the scratch-writing callback on #70 and stopped before refreshing the statistics. The saved run still had `calibration = 47`, incorrectly owned by the post-processor, with a stored fingerprint. `src/StatLayers.jl:198` exempts files with a fingerprint from migration. Opening the file under #72 and registering an unrelated simulation statistic then removed the calibration from disk. Opening an unmodified copy of the 0.9 file directly under #72 preserved it. The faulty record predates #72. Add a migration or repair path for files written by #70 with this bad ownership, and document the affected upgrade path so users can preserve or recover the solver statistic. [Migration](../src/StatLayers.jl#L194) · [Stored-ownership upgrade](2026-11-26-main-89be634-codex-evidence/ownership-upgrade.txt) · [Direct-upgrade control](2026-11-26-main-89be634-codex-evidence/ownership-upgrade-control.txt)
2. **Minor. L2 can still lose precision when forming the measure underflows before the total returns to a normal value.** `src/StatCalculation.jl:81–82` forms the spacing product in Float64, and `:104–107` accepts its final value when normal. On a three-dimensional unit field with spacings `2e-162, 2e-162, 1e308`, the product's intermediate rounding made the norm about 11.1 percent too large. The BigFloat control gave `5.65685424949238e-8`, versus `6.286911138810515e-8` on both revisions. Take the logarithmic path when any partial product enters the subnormal range, or accumulate the spacing scales before multiplying. [Measure](../src/StatCalculation.jl#L79) · [BigFloat control](2026-11-26-main-89be634-codex-evidence/l2-edges-head.txt)
