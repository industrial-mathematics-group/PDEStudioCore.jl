## Findings (new in round 2)

### N1. Medium — CONFIRMED — Tuple-suffix sweeps turn Bool (and every non-`Int` integer) tuple entries into `Int`
- Where: `src/Simulations.jl:144` (`task[base_key] = all(x -> x isa Integer, arr) ? Tuple(Int.(arr)) : Tuple(arr)`).
- What: `Bool <: Integer`, so a flag tuple such as `:periodic => (true, false)` swept with `:periodic__x => [false, true]`
  gives `(0, 0)` and `(1, 0)`, **including the entries that were not swept**. A solver doing `if periodic[1]` throws
  `TypeError: non-boolean (Int64) used in boolean context`, so every task of the sweep fails. `Int32`/`UInt8`
  tuples become `Int64` tuples (an `UInt64` entry above `typemax(Int)` makes `generate_tasks` throw an `InexactError`).
  It also contradicts `docs/src/advanced_config.md:38` ("identical to those of an explicit tuple sweep"): for Bool
  tuples the hash differs too (`"(1, 0)"` vs `"(true, false)"`).
- Evidence: `psc/probe_misc.out`: `[t[:periodic] for t in tasks] = [(0, 0), (1, 0)]`; Int32 tuple → `Tuple{Int64, Int64}`.
- Fix: keep the element values as they are (`Tuple(arr)` already gives `Tuple{Int, Int}` for Int entries), or only
  convert when every entry is an `Integer` but not a `Bool`. The Bool case cannot have working cached data today
  (the solver gets Ints), so changing it there costs nothing; for `Int32` tuples hashes are unchanged either way
  (`val2str(Int32(5)) == "5"`).

### N2. Medium — CONFIRMED — Post-processing is re-applied to already post-processed data on every run, and the statistics are never refreshed
- Where: `src/Simulations.jl:376-384` (pass 3 runs for every task, cached or not), `:273-289` (`_post_task` saves the
  modified data and keeps `evaluated_stats`); `docs/src/advanced_config.md:60` ("Mutate the data as you like").
- What: pass 3 loads every dataset from disk and calls `config.postprocess` again on each `run_all_simulations` call,
  including runs where everything was cached. A post-processor that changes the solution (normalising, filtering,
  adding an offset) is compounded once per call. And because pass 2 runs *before* pass 3, the statistics stored in the
  file describe the pre-post-processing solution; on later runs they are present in `stat_keys`, so they are never
  recomputed. The documentation invites exactly this use.
- Evidence: `psc/probe_post.out`: post-processor `data.u = 2 .* data.u; true` on `u ≡ 1`: after run 1 `u = 2`, after a
  second (fully cached) run `u = 4`; the stored `:mass` stays `1.25` (the mass of `u ≡ 1`) while the stored solution
  has mass `5.0`.
- Fix: run pass 3 only for datasets produced in this call (or record "postprocessed with <name>" in the file and skip
  those), and/or run the statistics after post-processing (or recompute them when post-processing returns `true`).
  At minimum, document that post-processing must be idempotent and must not change `u`.

### N3. Low/Medium — CONFIRMED — The new atomic rewrite degrades user-stored entries of types not loaded in the current session (regression of the round-1 #2 fix)
- Where: `src/IOUtils.jl:129-152` (`_update_entries!` copies every entry by load + store via `_copy_entry!`, `:175-185`),
  reached from `load_sim_data(…, :eulerian/:lagrangian)` with `enable_cache!(true)` (`:315, :327`) and from every stats
  pass (`src/StatCalculation.jl:254`).
- What: before the fix, conversion caches and the bookkeeping flags were appended in place, leaving the other entries
  untouched. Now the whole file is rewritten from loaded values. An entry whose type is not defined in the reading
  session (user metadata `save_sim_data(d; metadata = Dict("note" => UserNote(3)))`, a GUI session, or a pipeline that
  does not load the user's package) is loaded as `JLD2.ReconstructedStatic{…}` and written back as that, so it is
  permanently changed, even for the session that defines the type. Merely *viewing* a conversion with caching on does
  this. `docs/src/data.md:82` promises that other entries "you stored yourself" are kept. (`_write_sim_file`'s
  carry-over has the same property, but only on explicit overwrites; it at least catches failures with a warning,
  whereas `_update_entries!` has no `try` around the copy, so an entry that cannot be re-written makes a successful
  conversion throw.)
- Evidence: `psc/probe_copy_*`: process A saves the note; process B (no `UserNote`) loads `:eulerian (9, 2)` with the
  cache on — JLD2 warns "type Main.UserNote does not exist in workspace; reconstructing", the cache is written; process
  C, which defines `UserNote`, now reads `JLD2.ReconstructedStatic{:UserNote, (:a,), Tuple{Int64}}`
  (`psc/probe_copy.out`).
- Fix: skip the rewrite (and the cache write) when an entry comes back as a `JLD2.Reconstructed*` type (warn instead),
  or store caches/bookkeeping in a sidecar file so the data file is only rewritten on real data changes.

### N4. Low — CONFIRMED — `calculate_all_stats!(save = true)` does not save statistics added with `add_stat!` (docstring rewritten in 518e1b2 says it does)
- Where: `src/StatCalculation.jl:211-213` (docstring: "With `save = true` the dataset is saved, unless …"), `:253`
  (`_save_sim_data(sim_data, changed, …)`: only rewritten when a *registered* statistic changed).
- What: `calculate_all_stats!(d)`; `add_stat!(d, :runtime, 1.5, Symbol[])`; `calculate_all_stats!(d)` → the file
  exists and nothing registered changed, so the data is not rewritten and `:runtime` never reaches the disk.
  Same for any other in-memory change of the stats dictionary. Pre-existing behaviour, but the new docstring states the
  opposite.
- Evidence: `psc/probe_addstat_save.out` (`haskey(load_sim_data(p).stats, :runtime) == false`).
- Fix: compare the stats with the stored `stat_keys` (or treat the call as `overwrite = true` when the dataset was
  verified native and its stats differ), or document "saved if statistics were (re)computed; use `save_sim_data(d;
  overwrite = true)` for other changes".

### N5. Low — SUSPECTED — Lost updates between processes that rewrite the same file
- Where: `src/IOUtils.jl:129-152` (`_update_entries!`: read, write a copy, rename), `:190-219` (`_write_sim_file`).
- Reasoning: with unique temp names (round-1 #13), concurrent writers no longer corrupt each other's temp file, but
  every write is read-modify-rename without a lock or an "unchanged since read" check, so the last rename silently
  wins. Example: a PDEStudio session with `enable_cache!(true)` converts the old `raw`, then `_append_key!` copies the
  file *as it is now* (which a pipeline stats pass may just have rewritten) — fine — but if the pipeline renames its
  rewrite after the GUI read the file, the GUI's rename puts back the old statistics; or the GUI caches a conversion
  computed from the old `raw` next to the new `raw` (stale cache that is never invalidated). Not reproduced.
- Fix: an advisory lock file per data file (`mkpidlock` from FileWatching / `flock`), or check `stat(path).inode/mtime`
  before the rename and retry.

### N6. Low — CONFIRMED — Saving advances the user's default RNG stream
- Where: `src/IOUtils.jl:124` (`_tmp_path` uses `rand(UInt64)` from the task-local default RNG).
- What: every save, stats bookkeeping write or cache write draws from the caller's RNG. With `Random.seed!(1)` before a
  serial sweep, the random numbers a solver sees depend on how many writes happened before it (e.g. on which earlier
  tasks were cached or had statistics computed).
- Evidence: `psc/probe_rng.out`: `seed!(1); rand()` = 0.0734 vs `seed!(1); save_sim_data(d); rand()` = 0.3492.
- Fix: use `Random.RandomDevice()`, a module-level counter + `Threads.threadid()`, or `mktemp(dirname(path))`.

### N7. Low — CONFIRMED (timing) — Unbounded work from `str2val` ranges at hashing time
- Where: `src/Serialization.jl:69` (`(:)` is a literal function), `:31-36` (`val2str` iterates every array element).
- What: `str2val("1:10^15")` returns a lazy `UnitRange` instantly, but normalising/hashing it (`_param_hash`, every
  lookup, every save) writes out every element: 0.65 s for `1:10^6`, so a CSV/GUI value `1:10^9` takes ~10 minutes and
  GBs of string, `1:10^15` never finishes. Same class as round-1 #9 (file-borne DoS), not covered by its fix.
- Fix: cap the length of ranges/arrays `str2val` returns (or reject `(:)` results above some length).

7. **NOT OK (reason inaccurate).** The comment says the in-container `nothing`/`missing` behaviour is left "because

   val2str(Nothing) == "Nothing"` (also `val2str([nothing])` equals the hash input of its normalised String form), so
   keeping `nothing` elements (round-1's suggestion) leaves every hash unchanged (`psc/probe_fixes.out`, testset

   normalised filters in `find_sim_data`/`delete_sim_data`/`rehash` matching. Either fix it with that caveat or correct
   the comment.
8. **OK.** `save_sim_data` docstring now states that `sim_data.params` is replaced by its normalised form. (The same
   mutation happens through `calculate_all_stats!(save = true)` and `run_smart_simulation`; their docstrings don't say so.)
9. **NOT OK.** `EnvDict()` is fixed (only `Dict`/`IdDict` are built; tested). The power bound is easy to bypass:
   - nesting: `(BigInt(10)^10000)^10000` is accepted (0.55 s, a 3.3·10⁸-bit number, 42 MB); one more level
     (`…^20`) needs ~1 GB and crashed a Julia process with a core dump under `ulimit -v 6 GB` (`psc/probe_bigpow.jl`);
   - other big types: `(BigInt(3)//1)^(10^7)` → `Rational{BigInt}` with 1.6·10⁷ bits in 0.25 s,
     `(BigInt(3) + 0im)^(10^6)` → `Complex{BigInt}` (`psc/probe_fixes.out`); the exponent can be raised freely.
   The test `str2val("BigInt(3)^(10^7)") isa String` only covers the direct case. Fix: bound the *result size*
   (e.g. `exponent * ndigits(base; base = 2)` and the operands' bit sizes, for `BigInt`, `Rational{BigInt}`,
   `Complex{BigInt}`, i.e. any number whose `widen`/precision is unbounded), or reject `^` with a non-`Int64`/`Float64`
   base. (`BigFloat` has fixed precision; including it in the check is harmless but unnecessary.) See also N7 (ranges).
10. **OK.** `:wave_height` returns NaN for an empty step, Float32-generic; the new test (empty second step: NaN height,

12. **OK.** `docs/src/statistics.md` states the rectangle rule and the `N/(N-1)` example correctly (u ≡ 1 on N nodes

13. **OK.** pid + 64-bit random suffix; `.tmp` files are ignored by `_data_files` and removed on error. Side effect: N6.

## Minor issues

- `src/IOUtils.jl:17`: `"evaluated_with_reference"` is not in `_MANAGED_KEYS`, so `save_sim_data(...; metadata =
  Dict("evaluated_with_reference" => …))` is accepted and an overwrite of the raw data (new solver run) keeps the old
  flag while dropping `evaluated_stats`. Harmless today (a missing `evaluated_stats` triggers the recompute), but it is
  simpler to manage both together.
- `src/Simulations.jl:22`: `_WARNED_REFERENCE_NAMES` is a global `Set` mutated without a lock; `generate_tasks` from
  several threads (frontends) could race.
- `src/Config.jl:354`: `_lookup_global` returns any global, not just functions; a non-function global with a solver's
  name gives a confusing `MethodError` later instead of "could not resolve".
- `src/ConversionUtils.jl:188-199`: axes with duplicate nodes pass `create_sim_data` (`issorted` allows ties) but make
  `Gridded` interpolation throw, so `load_sim_data(p, :eulerian, res)` fails for e.g. a time axis that records the
  initial state twice.
- `src/Constructors.jl:211-213`: Lagrangian spacing uses the *maximum* particle count over all steps, so `:mass` of a
  step from which particles left is underestimated (design; worth a sentence in the docs).

## Verdict

The round-1 fixes are mostly solid and come with regression tests that fail on the old code (1, 2, 3, 5, 6, 10). Two
handlings are not OK: the BigInt bound of #9 is bypassed by nesting or by `Rational`/`Complex` big numbers, and the
reason given for deferring #7 is wrong (keeping `nothing` in containers would not change any hash). The atomic-rewrite
fix for #2 introduced a small regression: user entries of types that aren't loaded get changed when a conversion is
cached or a stats pass runs (N3). New, independent of the fixes: tuple-suffix sweeps coerce Bool tuples to Int (N1),
and post-processing is re-applied on every run with statistics left stale (N2). Numerics and thread-count independence
are fine; the suite passes with 1 and 8 threads (410/410).

Findings (new): 0 high, 2 medium (N1, N2), 1 low/medium (N3), 4 low (N4, N5 suspected, N6, N7).
Round-1 handling: 11 OK (2 and 3 with residuals), 2 NOT OK (7, 9).
