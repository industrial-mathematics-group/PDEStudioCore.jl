## Findings

### 1. High — CONFIRMED — Nested type parameters multiply: the per-parameter cap of 256 does not bound the size of a type. A 55-character literal aborts Julia
- **Where:** `src/Serialization.jl:110-115`. The cap is per parameter, and `Core.apply_type` builds the type.
- **What goes wrong:** Each level of `NTuple{256, …}` passes the check. The type then reaches `Dict{K, V}()` at `:186-187`, `IdDict` or `getindex(T)` at `:109`, which make the compiler specialise on it. A tuple type of 256^k fields costs that much in LLVM.
- **Scenario:** a CSV cell or editor input `Dict{NTuple{256, NTuple{256, NTuple{256, Int}}}, Int}()`. LLVM throws `std::bad_alloc`, and the process dies with **SIGABRT → SIGSEGV**. `try/catch` cannot catch this, so the session is lost.
  - Also crash: `IdDict{NTuple{256, NTuple{256, NTuple{256, Int}}}, Int}()` and `Dict{Int, NTuple{256, NTuple{256, NTuple{256, Int}}}}()`.
  - Slow:

    | Literal | Characters | Cost |
    |:--|--:|:--|
    | `Dict{NTuple{256, NTuple{256, Int}}, Int}()` | 42 | compiles for more than 120 s (killed by `timeout`) |
    | `Dict{Int, NTuple{256, NTuple{256, Int}}}()` | | 8.9 s |
    | `NTuple{256, NTuple{256, NTuple{256, Any}}}[]` | | 5.0 s, then hashing 30.7 s |
    | `Dict{NTuple{256, NTuple{256, NTuple{256, Any}}}, Int}()` | | 16.8 s, then hashing 70.6 s |

  - Under the 8 GB limit, LLVM ran out of address space. Without a limit it would grow towards the 32 GB cgroup. I did not run that.
- **Evidence:**
  - `psc/probe_types.out` and `psc/probe_types2.out`: exit code 139.
  - `psc/probe_dict3.out`: `terminate called after throwing an instance of 'std::bad_alloc'`, at `one.jl:6` (the `str2val` call).
  - For comparison, `Dict{NTuple{256, NTuple{16, Int}}, Int}()` (4096 leaves) takes 1.7 s.
  - Non-concrete nestings are cheap: `NTuple{256, NTuple{256, Real}}` takes 0.1 s, and `…Union{Int, Nothing}…` 0.3 s (`psc/probe_types3.out`).
- **Fix:** bound the **size** of each type that `:curly` builds, not only its parameters.
  - After `Core.apply_type`, reject a concrete `DataType` whose `sizeof` is above a few KiB (e.g. `2^13`–`2^15` bytes). That is 1000–4000 Int leaves, which compiles in 0.5–1.7 s.
  - Inner `:curly` expressions are evaluated first, so `NTuple{256, NTuple{256, Int}}` (512 KiB) is rejected at its own level, before any container sees it.
  - Abstract tuple types are cheap, so they need no check.
  - With such a bound, the cap of 256 could be relaxed (see Finding 4).
- **Test:**
  - `@test str2val("Dict{NTuple{256, NTuple{256, Int}}, Int}()") isa String`
  - `@test str2val("NTuple{256, NTuple{256, Int}}") isa String`
  - Run these only after the fix: today the first one hangs, and the three-level form kills the test process.

### 2. Medium — CONFIRMED — Long tuple *values* used as Dict keys cause the same compile cost, without any type parameter
- **Where:** `src/Serialization.jl:186-187` (`T(values...)` for `Dict`).
- **What goes wrong:** the parameter cap only applies to written types. A tuple literal of n elements has type `NTuple{n, …}`. `Dict(key => v)` then compiles `setindex!`/hashing for that key type, and the cost is superlinear in n.
- **Scenario:** `Dict((1, 1, …, 1) => 1)` with 10^3 elements (3 KB) takes 0.6 s. With 10^4 elements (30 KB) it takes **55.8 s**. A 100 KB cell would take far longer (extrapolated, not run).
- **Evidence:** `psc/probe_values.out`. These are cheap:
  - plain tuples: 10^4 elements in 0.02 s; mixed types 0.14 s
  - `[(…)]` with 10^4 elements: 0.05 s
  - a Dict with a long tuple **value**: 0.55 s
  - `SA{Float64}[…]` with 3000 elements: 0.03 s
- **Fix:** before constructing a `Dict`/`IdDict`, apply the type-size bound of Finding 1 to the key and value types of the pairs, e.g. `typeof(p.first)`.
  - `val2str` writes such dicts as `Dict{NTuple{10000, Int64}, Int64}(…)`, which the cap already rejects. Rejecting the untyped form too costs nothing for round trips.
- **Test:** `@test str2val("Dict((" * join(fill("1", 10^4), ", ") * ",) => 1)") isa String`. Before the fix this takes about a minute.

### 3. High — CONFIRMED (pre-existing, outside this diff) — BigFloat escapes the size limits: short literals segfault in MPFR or build huge BigInts
- **Where:**
  - `src/Serialization.jl:141`: `_exact_bits(::Number) = 0` also covers BigFloat.
  - `:172-182`: `_LITERAL_FUNCTIONS` (`sin`, `cos`, `tan`).
  - `:192-193`: `T(values[1])` for `BigInt`, `Int128`, `Complex{BigInt}`, `Rational{BigInt}`.
- **What goes wrong:** Julia's MPFR exponent range is ±2^62, so `BigFloat(2)^(2^40)` is cheap and finite.
  - Converting it exactly (`BigInt(x)`, and `Int128`/`Complex{BigInt}`/`Rational{BigInt}`, which go through `mpfr_get_z`) allocates exponent-many bits.
  - The argument reduction of `sin`/`cos`/`tan` needs a precision of about the exponent.
- **Scenario:**
  - 26 characters: `BigInt(BigFloat(2)^(2^36))` → an 8 GiB allocation. Under a 6 GB limit it **segfaults in `mpfr_init2`**, uncatchable. With `2^38` it would ask for 32 GiB, the cgroup limit (not run).
  - Same crash: `cos(BigFloat(2)^(2^40))`, `tan(BigFloat(3)^(2^40))`, `sin(BigFloat(2)^(2^40) + 0im)`, `Int128(…)`, `Complex{BigInt}(…)`, `Rational{BigInt}(BigFloat(2)^(-2^36))`, and any call wrapping them, since arguments are evaluated before the function is checked.
  - Below the crash threshold:
    - `BigInt(BigFloat(2)^(2^28))` returns a **268-Mbit BigInt**, 256× the documented 2^20-bit limit, and hashing it takes 8.8 s.
    - `sin(BigFloat(2)^(2^26))` takes 17 s.
  - These are fine: `exp`, `log`, `%`, `^` and `BigFloat(2)^(2^62)` itself are fast (≤ 0.16 s), and `Int(…)` is a String.
- **Evidence:** `psc/probe_bigfloat.out`, `psc/probe_bigfloat2.out`, and `psc/probe_bigcrash.out` (stacks `mpfr_init2 ← mpfr_get_z ← BigInt ← _literal_call:193` and `mpfr_init2 ← mpfr_cos ← _literal_call:180`).
- **Fix:**
  - (a) Treat BigFloat like the exact types: reject finite, non-zero BigFloat arguments or results with `abs(exponent(x)) > _MAX_LITERAL_BITS`, also inside `Complex`. Do it in `_literal_call`, for every function argument and every `T(values[1])`.
  - (b) Also check `_exact_bits(result) <= _MAX_LITERAL_BITS` after every Number constructor.
- **Test:**
  - `@test str2val("BigInt(BigFloat(2)^(2^28))") isa String`
  - `@test str2val("sin(BigFloat(2)^(2^26))") isa String` (bounded: 17 s before the fix)
  - Add the 2^36/2^40 cases only after the fix, since today they kill the process.

### 4. Low — CONFIRMED — Legitimate values with an integer type parameter above 256 no longer parse (they did at 2cef67f)
- **Where:** `src/Serialization.jl:114`.
- **Scenario:** these values are written by `val2str` and now come back as Strings:
  - `[ntuple(_ -> 1.0, 300)]` → `NTuple{300, Float64}[…]`
  - the type `NTuple{300, Float64}`
  - `[SVector{300}(…)]`
  - `Dict(:a => ntuple(i -> i, 300))`
  - `Array{Float64, 300}`
  - `[SMatrix{17, 17}(…)]`, whose length parameter is `L = 289`

  `SVector{300, Float64}` parameters matter little. StaticArrays is meant for small sizes, and PDEStudio writes static vectors as `SA{T}[…]`, which has no written size: 3000 elements parse in 0.03 s. `SMatrix{17,17,…,289}` is the most plausible case.
- **Effect:**
  - Hashes do not change: the stored String is the same text `val2str` wrote.
  - The normalised parameter becomes a String instead of a value. This applies consistently to filters too, because they are normalised the same way.
- **Evidence:** `psc/probe_legit.out`.
- **Fix (optional):** with the type-size bound of Finding 1, the per-parameter cap can be raised (e.g. 4096). Only the `NTuple{2^62}`-style huge values need it, and Array's N needs its own bound (Finding 6).

### 5. Low — CONFIRMED — Rational step ranges are Strings (regression of 2cef67f, not of this commit)
- **Where:** `src/Serialization.jl:181`. `Base.checked_length` has no method for `StepRange{Rational}`, because `checked_sub(::Rational, ::Rational)` is undefined. The `MethodError` is caught, so the literal becomes a String.
- **Scenario:** `1//2:1//2:2` and `1:1//2:3` give Strings. Both were ranges at dfdcbac. `1//1:10//1` and `1//2:2` (unit step) still work.
- **Evidence:** `psc/probe_roundtrip.out` and the inline check in this review (dfdcbac's `str2val` returns `1//2:1//2:2//1`).
- **Fix:** for `StepRange{<:Rational}`, use `length` (Rational arithmetic is overflow-checked anyway), and keep `checked_length` for the others. Add `str2val("1//2:1//2:2") == 1//2:1//2:2` to the tests.

### 6. Low — CONFIRMED — `Array{T, N}` types with N up to 256 still cost seconds each when hashed
- **Where:** `src/Serialization.jl:114`. Previous finding 4 suggested bounding Array's N together with the reshape dims, but only reshape got `_MAX_DIMS`.
- **Scenario:**
  - `Dict{Array{Int, 256}, Int}()` hashes in 4.96 s (1.5 GiB RSS).
  - A tuple of four such Dicts with different N (120 characters) takes 17.8 s.
  - The cost is about 150 s per KB of text: bounded, but slow.
  - `Dict{Array{Int, 64}, Int}()` takes 1.1 s.
- **Evidence:** `psc/probe_arraydims.out`, `psc/probe_types2.out`.
- **Fix:** for `T <: AbstractArray` (and `CartesianIndex`/`CartesianIndices`), limit N to `_MAX_DIMS`.

## Addressed findings of reviews/2cef67f.md

1. **Integer type parameters / `NTuple{2^62, Int}` crash:**
   - OK for single parameters. `NTuple{2^62, Int}`, `Dims{257}` and `NTuple{-2^63, Int}` are Strings, `Val{2^62}()` still works, and the new test fails (segfaults) at 2cef67f.
   - NOT OK in general. Nesting multiplies the size: a 55-character literal still aborts the process (Finding 1). Long tuple values bypass the cap (Finding 2). BigFloat is a separate pre-existing crash class (Finding 3).
2. **Typed containers collecting many capped ranges:** OK.
   - No range can appear inside a vector, tuple, typed container, Pair, call, reshape or type parameter, and no other lazy array (`OneTo`) leaks into a typed container.
   - The 50-range literal allocates 0.1 MiB (382 MiB at 2cef67f).
   - Top-level ranges (`1:10`, `0:0.1:1`, `-5:5`) are still accepted.
   - `val2str` never writes ranges, so no round trip is affected.
   - The new `… isa String` test does not measure allocation and passes at 2cef67f as well. `[1:3, 4:6]` is the test that fails there.
3. **Negative reshape dims:** OK.
   - Since ranges can no longer reach `reshape`, its first argument is always an `Array`, for which Base rejects negative dims itself. The new check is defence in depth.
   - The new test (`reshape([1, 2], (-1, -2))`) passes at 2cef67f too. The range form of the old finding (`reshape(1:6, (-2, -3))`) was a `ReshapedArray` there and is a String now.
4. **Many reshape dims:** OK for `reshape` (at most 16). NOT OK for `Array{T, N}` types, which the old fix also named (Finding 6).
5. **Unreliable `@elapsed` test:** OK.
   - It was replaced by `@allocated(str2val("Vector{Float16}[0:2^26]")) < 2^20`, which failed at dfdcbac (previous review) and passes now.
   - The first call in a fresh process allocates 10.4 MB, from compilation. The test passes because earlier calls in the testset have compiled the path.

## Minor issues

- `src/Serialization.jl:114`: `abs(p) <= 256` accepts `typemin(Int)`, because `abs(typemin(Int)) < 0`. As a result, `Array{Int, -2^63}` and `Dict{Array{Int, -2^63}, Int}()` are accepted. This is harmless (`NTuple{-2^63, Int}` errors in Base, and the Array type is inert), but `-256 <= p <= 256` says what is meant.
- The `str2val` docstring (`:198-206`) still says "more than 10^6 elements in total, ranges included". It does not mention the new rules: ranges only as the whole value, integer type parameters ≤ 256 except in `Val`, and reshape with at most 16 non-negative dims. `docs/src/data.md:116` also lists the accepted literals without these rules.
- `_literal_parts` evaluates every argument before the function or type is checked, so `isa(BigInt(BigFloat(2)^(2^36)), Any)` crashes exactly like the bare literal. This is not a separate issue, but it means the fixes for Findings 1 and 3 must sit where values are built, not where calls are dispatched.

## Verdict

The change does what it set out to do for the cases the previous review named:
- A range is a literal only as the whole value. This cleanly closes the "typed containers collect many ranges" gap without affecting any `val2str` round trip (114/114 round trips, top-level ranges still accepted).
- Single huge type parameters no longer crash.
- Reshape dims are bounded.
- The suite passes (432/432).

But the literal parser can still kill the Julia process from a short cell, in two ways:
- **Nested type parameters** (`Dict{NTuple{256, NTuple{256, NTuple{256, Int}}}, Int}()`, 55 characters) abort LLVM, and two levels compile for minutes. The per-parameter cap needs a bound on the size of the resulting type (Finding 1, high, the same class as the finding this commit fixes).
- **BigFloat with huge exponents** (`BigInt(BigFloat(2)^(2^36))`, `cos(BigFloat(2)^(2^40))`, 23–26 characters) segfaults in MPFR. This is older than this branch, but it is the same class of problem (Finding 3, high).

Smaller gaps:
- Long tuple Dict keys (Finding 2, medium).
- Lost round trips for parameters above 256 (Finding 4).
- Rational step ranges, regressed in 2cef67f (Finding 5).
- High-N `Array` types (Finding 6).

Findings: 2 high (1, 3), 1 medium (2), 3 low (4, 5, 6).

- 1: OK for single parameters, NOT OK for nesting.
- 2: OK.
- 3: OK.
- 4: OK for reshape, NOT OK for `Array{T, N}`.
- 5: OK.
