## Findings

### 1. Medium — CONFIRMED — `_literal_size` walks every element of a lazy `reshape` of a range: a short value hangs `str2val` (regression)
- Where: `src/Serialization.jl:130` (`_literal_size(x::Union{Tuple, AbstractArray}) = … sum(_literal_size, x)`) together with
  `src/Serialization.jl:139-141` (`reshape` accepts any `AbstractVector`, including a range, and returns a lazy `ReshapedArray`).
- What: `reshape(1:N, dims)` is an `AbstractArray` but not an `AbstractRange`, so `_literal_size` sums `1` over all N elements.
  This change removed the per-range cap in `_literal_call`, which used to reject `1:N` for N > 10^6 before `reshape` ran. The value is
  rejected in the end, but only after a walk of N elements.
- Scenario: a CSV or GUI value `reshape(1:2^48, (2^24, 2^24))` (31 characters) keeps `str2val` busy for about 10 min. With
  `reshape(1:2^62, (2^31, 2^31))` it is about 110 days. At f97198a both returned a String at once.
- Evidence: `psc/probe_reshape_timing.out` (2^40 elements: 2.28 s, 2^42: 9.49 s, linear). The 2^62 case, run inline with `timeout 120`, was killed
  while still inside `_literal_size` → `sum` → `mapreduce_impl` (from the stack trace printed on SIGTERM).
- Fix: check `length(x)` (O(1) for lazy arrays) before walking the elements, and stop as soon as the budget is exceeded. This
  also fixes Finding 2:
  ```julia
  function _literal_size(x::Union{Tuple, AbstractArray, AbstractDict})
      length(x) > _MAX_LITERAL_LENGTH && return length(x)
      n = 0
      for el in x
          n += _literal_size(el)
          n > _MAX_LITERAL_LENGTH && return n   # each term is checked, so n never overflows
      end
      return max(n, 1)
  end
  ```
  Test: `@test str2val("reshape(1:2^62, (2^31, 2^31))") isa String` (instant once the check is right).

### 2. Low — CONFIRMED — The whole-value element count overflows: two or more huge ranges get through
- Where: `src/Serialization.jl:130` and `:132` (`sum` in `Int`, no overflow check).
- What: the sum of range lengths wraps around. `(1:9223372036854775807, 1:9223372036854775807)` has size `-2`.
  `(1:2^62, 1:2^62, 1:2^62, 1:2^62)` has size `0`. The `Dict` and `Any[...]` forms behave the same way. `str2val` returns these values
  instead of a String.
- Consequence: limited. Every element range has at least 2^62 elements, so a later `val2str`/hash fails fast with an `ArgumentError`
  (the comprehension can't allocate that many elements). It does not hang (`psc/probe_hash_overflow.jl`: 0.26 s). So the limit is
  bypassed, but the result is an error during normalisation or hashing instead of a stored String. Code that iterates the value lazily
  (a user's solver) would still hang.
- Evidence: `psc/probe_literals.out`, testset "whole-value size" (6 of 7 cases are accepted, with sizes `-2`, `-4611686018427387904`,
  `0`, …).
- Fix: the early-exit loop of Finding 1. Test: `@test str2val("(1:9223372036854775807, 1:9223372036854775807)") isa String`.

### 3. Low — CONFIRMED — The reconstructed-type warning only sees top-level values
- Where: `src/IOUtils.jl:177` (`_is_reconstructed` checks `typeof(value)` itself), used in `_copy_entry!` (`:181-182`).
- What: an entry whose own type is unknown is warned about. If the unknown type sits inside a container, the entry is degraded with
  no warning from PDEStudioCore. JLD2's own "reconstructing" warnings still appear, so the docs' "(with a warning)" is not false.
  A `Dict` holding an unknown type comes back as `JLD2.SerializedDict` for good.
- Scenario: process A saves with `metadata = Dict("note" => UserNote(3), "notes" => [UserNote(1)], "dnote" => Dict("k" => UserNote(2)),
  "mnote" => MutNote(4), "snote" => Some(UserNote(5)), "tnote" => (UserNote(6), 1))`. Process B (without the types) calls
  `save_sim_data(load_sim_data(P); overwrite = true)`. PDEStudioCore warns for `note` and `mnote` only. In process C, which defines the
  types, all six entries are degraded: `Vector{JLD2.ReconstructedStatic{…}}`, `JLD2.SerializedDict`, `Some{JLD2.ReconstructedStatic…}`,
  `Tuple{JLD2.ReconstructedStatic…, Int64}`, and `MutNote` becomes a (static) `ReconstructedStatic`.
- Evidence: `psc/probe_reconstructed.out`.
- Fix (if it's worth it): check the type recursively, e.g.
  `occursin(r"JLD2\.(Reconstructed|SerializedDict)", string(typeof(value)))`. That covers element and parameter types, though not
  elements of `Vector{Any}`. The alternative is to say in `data.md` that the warning comes from JLD2.
  `value isa JLD2.AbstractReconstructedType` would be more direct than the name prefix for the top-level case.

## Addressed findings of reviews/f97198a.md

- **1 (power-bound overflow): OK.** The comparison by division is correct for every exponent type I tried. `2^62`, `2^63` (=
  `typemin(Int)`, where `abs` is negative and the check passes, but the power then throws a `DomainError` at once), `-2^63`,
  `Int128(2)^127`, `big(2)^100`, Float `1e7`/`NaN`/`Inf`, `Complex` and `Rational` exponents: all < 0.25 s, giving a String or a
  fixed-size result. The boundary is the same as with the product (`(BigInt(3)//1)^(2^19)` parses, `^(2^20)` does not). Typical
  literals still parse (`BigInt(10)^(2^18)`, `(BigInt(2)//1)^-3`, `(1+2im)^3`, `1.5^(10^7)`, `2.0^(2^62)`). The new test fails (crashes)
  on f97198a.
- **2 (range cap per range): NOT OK.** The whole-value count catches the reported tuple of 20 ranges, and its test fails on f97198a.
  But the count can overflow (Finding 2). It also walks every element of a lazy `reshape(range)`. That turns a value which f97198a
  rejected at once into a CPU hang of minutes to months (Finding 1, a regression).
- **3 (user entries degraded by a data rewrite): OK as documented, with a gap.** The chosen fix (document it and warn instead of skipping)
  is one the review offered. `data.md` is accurate. The PDEStudioCore warning only covers top-level entries (Finding 3). The new
  two-process test is a regression test for the bookkeeping byte-copy from round 3. It passes on f97198a and does not exercise the
  rewrite path or the warning.
- **4 (symlinked data file): OK.** `_update_entries!` and `_write_sim_file` now replace the target of the link. Verified for absolute,
  relative and chained links, a symlinked `data/` directory with a relative save path, a stats pass and a conversion cache. The link stays,
  lookup by hash still finds it, and no `.tmp` is left (`psc/probe_symlinks.out`). A dangling link is replaced by a regular file. That is
  sensible, because `isfile` is false and the path is kept. `save_sim_data` still returns the link path, because `_save_sim_data` ignores
  the return value of `_write_sim_file`. The new symlink test fails on f97198a, but only `_update_entries!` is tested, not the
  `_write_sim_file` path.
- **5 (growth claim): OK.** "About its own size, a few hundred bytes to a few kB" matches the measured 138 B to 4.4 KB. The comment in
  `IOUtils.jl:132` agrees.

## Minor issues

- Behaviour change, not documented: the element limit now applies to every value, not only to ranges. A parameter array with more than
  10^6 elements (e.g. a `1001×1000` matrix, or `[rand(500_001), rand(500_000)]`) no longer round-trips through `_normalize_param`. It is
  stored in `"params"` as a (multi-MB) String. The hash is unchanged (`val2str` of that String is the same text), but loaded params hold a
  String instead of the array (`psc/probe_literals2.out`, "legit values"). Parameters that large are probably rare. The `str2val` docstring
  mentions none of the limits. Add a sentence.
- `test/test_data.jl:105-107`: the file path is interpolated into Julia source (`\"$foo_file\"`). A path with `"`, `$` or a backslash (Windows)
  breaks the test. Passing it through `ARGS` is more robust. CI runs Linux, so this is low risk.
- `_update_entries!` on a file holding entries of unknown types prints JLD2's "type … does not exist in workspace; reconstructing"
  warning. It comes from the first write in `jldopen(tmp, "a+")` (`psc/probe_warn_source.out`), and it appears twice in the suite log. The
  entry itself is not changed (the test checks this), but users will see an alarming warning on every bookkeeping update of such files.
  Possibly suppress it with `Logging.with_logger` around the write, or document it.
- `src/Serialization.jl:142`: the comment "Exact powers and ranges grow with their arguments" is stale. Ranges are no longer checked
  there, only in `str2val`.
- Unchanged (pre-existing): `rehash_sim_data` of a symlinked file whose hash changes writes a new regular file and deletes only the link.
  The old target stays orphaned in place.

## Verdict

Findings 1, 4 and 5 of the previous review are fixed correctly. The power bound is now overflow-free for every exponent type, and the
symlink handling is correct and keeps lookup by hash working. Finding 3 was addressed by docs and a warning, which was an accepted option,
but the warning misses nested values. The new whole-value element count is the weak spot again. It overflows (low impact: a fast error
later instead of a String). It also walks lazy `reshape` arrays element by element, which brings back a hang from a 31-character value that
f97198a rejected at once (medium). One small change to `_literal_size` (check `length` first, exit early) fixes both. The suite passes
(419/419). Hash stability, the no-eval rule, atomic writes and Julia 1.12 compatibility are untouched.
