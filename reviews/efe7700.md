## Findings

### 1. Medium — CONFIRMED — A reference (or round-tripped) dataset at the native resolution silently overwrites the native simulation data
- Where: `src/StatCalculation.jl:234-247` (save branch of `calculate_all_stats!`), guard `src/IOUtils.jl:268-273`
  (`_is_native_representation`).
- What: the guard that should stop derived datasets from being saved over the native run only compares the
  representation kind and the shape of `u`. A dataset from `generate_reference_simdata(ref, params, domain, size(sim.u), :eulerian)`
  (or `convert_to_eulerian(convert_to_lagrangian(e), size(e.u))`) has the same kind, shape and params, so
  `calculate_all_stats!(ref, f)` (default `save = true`) runs `save_sim_data(ref; overwrite = changed)` and replaces
  the stored solver output with the exact solution. There is no warning.
- Scenario/evidence: `probe_refoverwrite.jl`: after `calculate_all_stats!(ref, exact)`, `load_sim_data(p).u[3, 2] = 0.105`
  (the exact solution) instead of the solver's `1.105`. The existing test (`test_data.jl:66-68`) only covers a
  different resolution `(10, 5)`, so it passes for the wrong reason.
- Fix: don't infer "native" from the shape. E.g. mark derived datasets (a field or a param-free flag set by
  `generate_reference_simdata`/`convert_*`/`resample_eulerian`), or compare the data against the stored `"raw"` only
  when `overwrite` would be true, or make `save` default to `false` unless the dataset was loaded from / produced for
  that file. At minimum, add the native-resolution case to the test.

### 2. Medium — CONFIRMED — In-place (non-atomic) writes into data files, contrary to the "atomic writes" invariant
- Where: `src/IOUtils.jl:123-139` (`_append_key!`, `_set_key!`, both `jldopen(path, "a+")`), used by
  `src/StatCalculation.jl:245-246` (`evaluated_stats`, `evaluated_with_reference` after every stats pass) and
  `src/IOUtils.jl:285, 297` (conversion caches with `enable_cache!(true)`).
- What: CLAUDE.md requires "Atomic writes ... keep it that way for every new writer", and `docs/src/data.md:82` states
  "Writes are atomic ... rewriting a file does not grow it". These two helpers modify the existing file in place; `_set_key!`
  even does `delete!` followed by a write, so an interrupt between the two loses the entry, and a crash during the
  append can leave the JLD2/HDF5 structure of the *whole* file (including `"raw"`) damaged. A reader in another
  process (e.g. the PDEStudio GUI or a second pipeline) can see a half-written file. JLD2 does not reclaim deleted
  space, so each changed value grows the file.
- Evidence: `probe_inplace.jl`: the inode is unchanged by a stats pass that only updates `evaluated_with_reference`
  (`ino2 == ino3`), and 20 toggles of `_set_key!` grow the file from 38609 to 41231 bytes.
- Fix: write `evaluated_stats`/`evaluated_with_reference` as part of `_write_sim_file` (pass them as metadata to the
  `save_sim_data` call that already happens), and when nothing else changed, rewrite through the temp-file path; do
  the same for conversion caches (copy + add key + rename).

### 3. Low/Medium — CONFIRMED — Post-processing that returns `true` makes every cached rerun reload, recompute and rewrite every file
- Where: `src/Simulations.jl:251-262` (`_post_task` → `save_sim_data(...; overwrite = true)`), `src/IOUtils.jl:17, 186`
  (`"evaluated_stats"` is a managed key and is not carried over; `"evaluated_with_reference"` is not managed and is).
- What: pass 3 rewrites the file and drops `evaluated_stats`. On the next `run_all_simulations(cfg; calculate_stats = true)`
  `_needs_stats` sees the all-NaN-dropped statistics (e.g. error stats without a reference) as never evaluated, reloads
  the data and recomputes; then pass 3 runs again on the cached data and rewrites the file again, dropping
  `evaluated_stats` again. A sweep is never "fully cached". The two flags are also inconsistent with each other
  (one survives the rewrite, the other doesn't).
- Evidence: `probe_pipeline.jl`, testset 2: after one run, `haskey(file, "evaluated_stats") == false`,
  `_needs_stats(...) == true`, and the file's mtime changes on a second, fully cached run.
- Fix: carry `evaluated_stats` over when the rewrite comes from post-processing (the raw solution is unchanged), or
  re-set it after `_post_task` saves; treat both flags the same way.

### 4. Low/Medium — CONFIRMED — Methods whose name merely contains a reference keyword are silently never run
- Where: `src/Simulations.jl:14-17` (`is_reference_method`), `:146` (filter in `generate_tasks`), `src/Config.jl:68`.
- What: any `_`-separated word that *starts with* `exact`, `analytic`, `reference`, `baseline` or `true` marks the whole
  method as a reference: `:godunov_exact_riemann`, `:godunov_exact_rs`, `:analytical_jacobian`, `:true_upwind`,
  `:reference_free_mood` are all skipped. In a hyperbolic-PDE package "exact Riemann solver" is a common method name.
  No warning is logged, and the constructor's warning is suppressed for such names too.
- Evidence: `probe_refnames.jl`: a config with methods `:godunov_exact_riemann` and `:upwind` produces one task (upwind)
  and no log message at `Warn` level.
- Fix: at least `@warn` once per skipped method in `generate_tasks`, ideally match only whole words (`exact`, `analytic(al)`,
  `reference`) as the *first* word, or let a method opt in/out explicitly (`:reference => true`). This changes which
  tasks run, so list it as a behaviour change.

### 5. Low — CONFIRMED — `test_advection_1d` docstring is false: Lax–Friedrichs *is* exact at `cfl = 1`
- Where: `src/Examples/advection_1d.jl:187-188` ("at `cfl = 1` upwind and Lax–Wendroff are exact; Lax–Friedrichs isn't").
- What: the implemented LF update `(l + r)/2 − ν/2 (r − l)` reduces to `l` at ν = 1, the exact shift, like upwind and
  Lax–Wendroff. The repo CLAUDE.md requires the examples' docstrings to be true (PDEStudio's quick start uses them).
  `test/test_examples.jl:58` checks only upwind and LW at ν = 1, so the false part is untested.
- Evidence: `probe_examples.jl`: max error at cfl = 1 is 7.8e-16 for all three schemes. At cfl = 0.25/0.5/0.75 the
  ordering LW < upwind < LF holds (e.g. 0.0031 < 0.094 < 0.256 at 0.5).
- Fix: e.g. "at `cfl = 1` all three schemes are exact shifts; below it Lax–Friedrichs is the most diffusive", and add
  LF to the ν = 1 test.

### 6. Low — CONFIRMED — Tuple-suffix sweeps on non-tuple parameters crash or change the parameter's type
- Where: `src/Simulations.jl:110-124` (`generate_method_tasks`), `:68-73` (`_split_varied_key`).
- What / scenarios (`probe_pipeline.jl`, testset "tuple suffixes"):
  - `:N__all` or `:N__x` on a scalar `:N` throws `MethodError: no method matching Vector{Any}(::Array{Any, 0})` from
    `collect(Any, 10)`; because `generate_tasks` runs outside the per-task `try`, `run_all_simulations` aborts before
    any task, with an unhelpful message (easy to trigger from a GUI sweep editor).
  - A vector parameter `[10, 10]` swept with `:Ns__x` becomes the tuple `(20, 10)` (type and hash change).
  - Padding beyond the tuple length mixes float zeros into integer tuples: `:Ns__4` on `(10, 10)` gives `(10, 10, 0.0, 5)`.
  - A parameter whose own name ends in a suffix (`:dt__1`) cannot be swept: the varied values are ignored and the
    "does not appear in the parameters of any active method" warning is misleading.
- Fix: if `haskey(task, k)` for the full key, treat it as an ordinary key; otherwise require the base value to be a
  `Tuple` (or keep the container type of an `AbstractVector`) and throw a clear `ArgumentError` for scalars and
  out-of-range indices instead of padding.

### 7. Low — CONFIRMED — `nothing`/`missing` inside containers are not normalised to themselves; several distinct values share a hash
- Where: `src/Serialization.jl:149-154` (generic struct branch writes `nothing` as `"Nothing"`, `missing` as `"Missing"`),
  `:266-268` (only top-level `nothing`/`missing` are special-cased).
- What: `get_clean_params` (and therefore every saved `"params"` entry and `sim.params` after saving) turns
  `(1, nothing)` into `(1, Nothing)` (the *type*), `[nothing]` into the String `"Nothing[Nothing]"` and `[1, missing]`
  into the String `"Union{Missing, Int64}[1, Missing]"`. Anyone who reruns from stored params (GUI, `find_sim_data`
  filters with the original value) gets different values. Hash collisions (by design of `val2str`, but undocumented):
  `"1"` vs `1`, `":upwind"` vs `:upwind`, `"Float64"` vs `Float64`, `"<empty>"` vs `""`, `(1, nothing)` vs `(1, Nothing)`,
  `0.1f0` vs `0.1`.
- Evidence: `probe_serialization.jl` (2 `@test_broken` show the round-trip failures; 6 passing tests show the collisions).
- Fix: hashes must stay stable (CLAUDE.md), so leave `val2str` alone; but the *stored* value can be fixed without
  changing hashes by normalising container elements recursively in `_normalize_param` (keep `nothing`/`missing`
  elements as they are). Document the string/value collisions next to `calculate_hash`.

### 8. Low — CONFIRMED — `save_sim_data` silently rewrites the caller's `sim_data.params`
- Where: `src/IOUtils.jl:219-221` (same pattern in `src/DataManagement.jl:222-224` for rehash, which is fine there).
- What: saving replaces the dataset's params by their normalised form, so a `Float32` parameter `0.1f0` becomes the
  `Float64` `0.1` (a different value, `Float64(0.1f0) != 0.1`), tuples containing `nothing` change (finding 7), SVector
  parameters become `Vector`s, etc. The dataset returned by `run_smart_simulation` and every dataset passed through
  `calculate_all_stats!(…; save = true)` is affected. The `ESimData` docstring says `params` are "the parameters that
  produced the data".
- Evidence: `probe_serialization.jl`, testset "save_sim_data mutates the caller's params".
- Fix: document it in `save_sim_data`, or save a normalised copy and leave `sim_data.params` alone (the file lookup
  already normalises on every query).

### 9. Low — CONFIRMED — `str2val` can return live global objects and unbounded computations
- Where: `src/Serialization.jl:178-186` (`_literal_type` accepts any `Type` bound in `Core`/`Base`/PDEStudioCore),
  `:232-234` (`T <: AbstractDict` with zero pairs calls `T()`), `:229-230` (arithmetic on any `Number`).
- What: no code is evaluated (I could not find a path to `eval`/`include`/calls of arbitrary functions — the invariant
  holds), but a CSV/config value `EnvDict()` yields the process `ENV` object itself (secrets in the parameter dict,
  shown by frontends before normalisation), and `BigInt(3)^(10^7)` is computed (0.1 s; `10^10` would need GBs and
  minutes) — a file-borne denial of service.
- Evidence: `probe_serialization.jl`: `str2val("EnvDict()") === ENV`; the BigInt power takes 0.10 s and has 4.77 M digits.
- Fix: whitelist the dictionary types (`Dict`, `IdDict`, `OrderedDict`-like) and the constructible types, and bound
  `^` (e.g. reject results/exponents above a size limit).

### 10. Low — CONFIRMED — The `:wave_height` preset throws on an empty Lagrangian time step, which aborts all statistics for that dataset
- Where: `presets/hyperbolic.jl:34-36` (`reduce((a, b) -> max.(a, b), u)` without `init`).
- What: a Lagrangian step with zero particles (all particles left the domain / were removed) gives
  `ArgumentError: reducing over an empty collection is not allowed`. Because the exception propagates out of
  `calculate_all_stats!`, the pipeline logs "Statistics failed" and saves *none* of the statistics of that run. The
  other presets handle empty steps (`sum` of an empty `Vector{SVector}` is zero).
- Evidence: `probe_pipeline.jl` / `probe_inplace.jl` ("empty particle step message").
- Fix: `isempty(u) && return fill(NaN, …)` or `reduce(...; init = fill(-Inf))`; consider catching per-statistic errors
  in `calculate_all_stats!` so one failing statistic doesn't drop the others.

### 11. Low — CONFIRMED — Documentation that contradicts the code
- `README.md:116` ("`postprocess`: Name of a function `data -> Bool` deciding whether a result is saved") and
  `src/Config.jl:16` ("return `true` to save"): the data is always saved in pass 1; the return value only decides whether
  the *modified* data is rewritten (`docs/src/advanced_config.md:60` describes it correctly). `probe_pipeline.jl`,
  testset 1: a post-processor returning `false` still leaves the run on disk.
- `README.md:40, 94`: "wave position" — the preset has `:wave_height` (maximum value), no position statistic.
- `calculate_all_stats!` docstring (`src/StatCalculation.jl:210`): "Statistics added with `add_stat!` are never touched",
  while `add_stat!`'s own docstring (`:119-120`) and `_sync_registry!` replace them when the same name is registered
  globally with other kept dimensions or with `force_overwrite = true`.
- `docs/src/data.md:82` ("Writes are atomic", "does not grow it") — see finding 2.

### 12. Low — numerical note (documented behaviour, but worth stating in the statistics docs)
- Where: `src/Constructors.jl:91-93` (spacing = mean node distance), presets `sum(u .* measure)`.
- What: all integrals are node sums times the mean spacing, i.e. a rectangle rule over *all* nodes. That is exact
  (spectrally accurate) for periodic grids without the duplicate endpoint (the advection/Burgers examples) and harmless
  when the boundary values are zero (heat, Poisson), but on grids that include both endpoints with non-zero boundary
  values it over-counts by about `(N+1)/N` per dimension: `u ≡ 1` on `[0,1]×[0,2]` with 9×5 nodes gives
  `mass = 2.8125` instead of `2` (`probe_edge.jl`). Convergence orders are unaffected, absolute norms/masses are not.
- Suggestion: say so in `docs/src/statistics.md` next to `get_integration_measure`, or offer a trapezoid-weighted measure.

### 13. Low — SUSPECTED — Fixed temp-file name is not safe for concurrent writers of the same file
- Where: `src/IOUtils.jl:175` (`tmp = path * ".tmp"`).
- Reasoning: within one process, `generate_tasks` deduplicates by hash, so two threads never write the same file. Two
  processes sharing a save path (e.g. several cluster jobs, or GUI + pipeline) that rewrite the same existing file
  (`overwrite = true`, stats pass, post-processing) open the same `.tmp` with `"w"`, so one truncates the other's
  half-written file and a corrupt file can be renamed into place. Not reproduced.
- Fix: unique temp names (`mktemp(dirname(path))` / pid + random suffix), still renamed atomically.

## Minor issues

- `src/IOUtils.jl:83-89`: every lookup (`_find_file`, `does_sim_data_exist`, `get_file_name`) does `readdir` + a regex
  per file + an `mtime` sort; a pipeline does several lookups per task, so a sweep is O(tasks × files) system calls.
  Fine for hundreds of files, slow for tens of thousands.
- `src/Serialization.jl:150`: custom structs are written as `typeof(v).name.name(...)`, dropping type parameters and
  module, so `Foo{1}(a=1)` and `Foo{2}(a=1)` (or `A.Foo` and `B.Foo`) share a hash (can't change without rehashing).
- `presets/hyperbolic.jl:87`: `:mass_error` silently floors at `1e-9` (for log plots, presumably); `:relative_mass`
  uses an absolute `1e-9` threshold on the reference mass. Neither is documented.
- `src/StatCalculation.jl:160-169`: `is_all_nan` drops a multi-component statistic entirely if *one* component is NaN
  everywhere (e.g. a relative error of a component whose exact value is zero).
- `src/StatCalculation.jl:25-39`: a stat registered with a dimension name the dataset doesn't have (typo `:tme`,
  or `:y` on 1D data) silently becomes a scalar over everything.
- `src/IOUtils.jl:232-238`: `save_sim_data(...; metadata)` drops `metadata` without a message when the file exists
  and `overwrite = false`.
- `src/ConversionUtils.jl:116` / `:45-48`: for a spatial dimension with resolution 1 the scatter "spacing" is
  `one(T)` in physical units, which enters the smoothing radius (huge for small domains, tiny for large ones).
- `src/Examples/_main.jl:124-127`: `_time_grid` can exceed `dt_max` by ~1e-9 relative (the `- 1e-9` tolerance), so a
  diffusion number at the stability limit can be 0.5·(1 + 1e-9); harmless in practice.
- `convert_to_lagrangian` / reference particles share one position vector for all steps (`fill(points, nt)`); documented,
  but mutating `x[1]` mutates every step.
- Poisson example: at `N = 16` Gauss–Seidel's error after 200 sweeps (2.8e-3) is *below* SOR's (3.2e-3) because GS
  approaches the discrete solution from below and crosses the exact one; the suite tests at `N = 32`, where the
  claimed ordering holds. Not a bug, just a fragile spot if the defaults change.

## Verdict

The package is in good shape: the core data model, constructors, conversions and statistics are careful and
generic (Float32 is kept end to end, D = 1/2/3/4, static and transient), results are independent of the thread count,
`str2val` does not evaluate code, the hash format is pinned by tests, and all six built-in examples behave as their
docstrings say with one exception (Lax–Friedrichs is exact at `cfl = 1`). The suite (386 tests) passes.

The real defects are in the storage layer: a derived dataset at the native resolution can silently replace the
solver output (finding 1), and the stats pass writes metadata into data files in place, which breaks the atomic-write
invariant (finding 2). Post-processing interacts badly with the stats bookkeeping (finding 3). The method-name
heuristic can silently skip real methods (finding 4). The rest are low-severity robustness and documentation issues.

Findings: 0 high, 2 medium (1, 2), 2 low/medium (3, 4), 9 low (5–13, of which 13 is suspected).
