## Findings

### 1. F5 is not fixed: every post-processing record update still adds a full copy of the metadata (low, CONFIRMED)

- **Where:** src/IOUtils.jl `_update_metadata!`, which calls `_set_key!(path, "metadata", md)` and then `_update_entries!` (append mode: replaced entries leave their space behind).
- **What:**
  - Upgrading first removes the duplicated top-level entries, but the large user entry now lives inside `"metadata"`.
  - Each record update replaces the whole `"metadata"` entry by appending, so the file grows by the full metadata size per update. On a 0.4 file with a large user entry, the growth is exactly what F5 reported. Each further post-processor name adds another copy, and this also holds for native v3 files with large metadata.
  - The new docs ("keep it small") soften this, but the commit message's claim ("no copies of large legacy entries on record updates") does not hold.
  - The new test (`filesize(...) < 2 * size_p`, small fixture) passes on 6faaec6's src too, so it can't detect the problem.
- **Evidence:** `new/big04.jl`: load 76.5 MiB; file 76.3 → 152.6 (after `noop`, now v3) → 228.9 MiB (after `noop2`). The 6faaec6 numbers are identical.
- **Fix:**
  - When `_update_metadata!` has to upgrade a file, apply the changes inside that single rewrite: load raw with its metadata, apply the changes, call `_write_sim_file(path, raw, entries, path)`. The first record then costs one rewrite and no copy.
  - For v3: rewrite atomically instead of appending when the old `"metadata"` entry is large, or store `:postprocessed` as its own small entry.
- **Test:** a 0.4 fixture plus a 10^6-element user entry. Run two post-processors with a `nothing` return and check that the file size stays near the original, not merely `< 2×`.

### 2. A legacy entry that can't be read now blocks every rewrite of its file, including post-processing (low, CONFIRMED, regression vs 6faaec6)

- **Where:** src/IOUtils.jl `_write_sim_file`, line 364:
  ```julia
  legacy && !(k in _BOOKKEEPING_KEYS) && !(old[k] isa JLD2.Group) && continue
  ```
  `old[k]` is evaluated outside the `try` that guards `_copy_entry!`.
- **What:**
  - For a legacy `previous` file, every top-level entry is fully read just to test whether it is a group. One entry that throws on read aborts the whole write.
  - Since `_update_metadata!` now upgrades legacy files first, a post-processor that returns `nothing` fails on every run for such a file. 6faaec6 ran it.
  - `save_sim_data(...; overwrite = true)`, statistics rewrites and rehash throw. The error doesn't name the entry.
  - `upgrade_sim_data` reports `:unreadable`, while the data loads and the pipeline treats the file as cached.
  - `_file_metadata` already skips such entries (with only a `@debug` message), so the file loads fine. Only writes fail.
  - Secondary cost: each large legacy entry is read once more during the rewrite.
  - JLD2 reconstructs unknown types instead of throwing (checked), so the trigger is a damaged entry or a package type whose custom `rconvert` fails.
- **Evidence:** `new/attack.jl` part A plus `attackA2.jl` (custom `JLD2.writeas`/`rconvert` that throws):
  - 278c925: `postprocessing => Dict(:failed => 1)` "Pkt: format changed"; save overwrite FAIL; the stack trace ends at `_write_sim_file IOUtils.jl:364`.
  - 6faaec6: post-processing `:ran`; save succeeded and dropped `"pkt"` with the carry-over warning.
- **Fix:** decide group-ness inside the guard, e.g. `isgrp = try old[k] isa JLD2.Group catch; false end`. Skip unreadable legacy entries with a `@warn` naming them, as the `_copy_entry!` failure path does. If an internal JLD2 group check is available, use it to avoid reading values.
- **Test:** a 0.4 fixture plus an entry whose `rconvert` throws. Check that the post-processing record (`nothing` return) is written and that the entry is reported in a warning.

### 3. `_legacy_records!` also rewrites 0.4 user entries named `"postprocessed"`/`"provenance"` (low, CONFIRMED)

- **Where:** `_file_metadata`, legacy branch, which calls `_legacy_records!` for every format below 3.
- **What:**
  - 0.4.4 never wrote these entries (`git grep` at `origin/main_dev`: no provenance/record code). In 0.4 files they are ordinary user entries; only the unreleased format 2 used them.
  - A user Dict `"postprocessed" => Dict("smoothing" => "done", "passes" => 3)` is read as an empty `Dict{Symbol, Any}()`. Upgrading stores it that way, so the data is lost for good. The first post-processing run now does that upgrade by itself.
  - Dict values would be taken as post-processing records (reported as `:outdated`).
  - A user `"provenance"` Dict gets Symbol keys.
  - 6faaec6 kept both verbatim.
- **Evidence:** `new/attack.jl` part B: `B load => (Dict{Symbol, Any}(), Dict(:lab => "B", :instrument => …))`, and the same after upgrade.
- **Fix:** apply `_legacy_records!` only when `_format_version(file) == 2`.
- **Test:** a 0.4 fixture plus a `"postprocessed"` Dict entry. It comes back unchanged as `metadata[:postprocessed]`.

### 4. v3: one unreadable value in `"metadata"` makes the dataset unloadable and fails its task on every run (low, CONFIRMED, from 6faaec6, not a regression)

- **Where:** `_file_metadata`, v3 branch: `v = file["metadata"]` has no guard. Legacy entries are guarded one by one.
- **What:**
  - `_load_key` fails, so `load_sim_data` fails for the whole dataset.
  - `does_sim_data_exist` is true, so the pipeline never recomputes the file. Pass 1 fails on every run, which contradicts the `upgrade_sim_data` docstring ("`:unreadable` … the pipeline recomputes them").
  - 278c925 fixed only the table.
  - The trigger is the same as in Finding 2: a package type whose deserialization changed.
- **Evidence:** `new/attack.jl` part E: `E load` FAIL "Pkt: format changed", `E exists => true`, pass 1 `failed`. The table works (6faaec6's table threw).
- **Fix:**
  - On a read error, load the data with empty metadata and a warning.
  - Make `_update_metadata!` and `_carry_metadata!` refuse to write when the stored metadata could not be read, so nothing is wiped.
  - Alternatively, document the limitation.
- **Test:** the probe as a test. The data loads with a warning, and a record update errors instead of replacing the metadata.

## Minor issues

1. **The version gate can be spoofed.** 0.4.4 files always have `dim_keys`. A 0.4 file with user entries `"format_version"` (an integer ≥ 3) and `"metadata"` counts as v3: only the `"metadata"` entry is read, the other user entries are hidden, and `upgrade_sim_data` reports `:current` (attack C). This needs two reserved names, so it is contrived; mentioned for completeness.
2. **Recording a post-processing upgrades a 0.4 file.** The data is rewritten and its conversion caches are dropped (attack D). This is the intended design, but data.md says `"metadata"` is "updated without loading the data" (line 99) and that 0.4 files are "read as they are" (line 106). One sentence there would cover it.
3. **0.4's top-level `"sources"` in v3 files is carried forever.** After a 0.4 writer rewrites a v3 file, its top-level `"sources"` is now kept as an invisible entry on every later rewrite; 6faaec6 dropped it (`new/dmx.jl`). Harmless, but junk. A `_format_version`-independent skip of the old pipeline names would restore the previous behaviour.
4. **`_update_metadata!` ignores what `_upgrade_file!` returns.** If the result is `:unreadable`, or another process puts a v1 copy back in between (the cp/mv of `_update_entries!`), it writes `"metadata"` into a version-1 file. There that entry is a user entry, and the record lands in `md[:metadata][:postprocessed]`. `_post_task` loads raw first, so I couldn't reach this path directly. Hardening: recheck the version after the upgrade and error out if it is still below 3.
5. **The `NullLogger` in `_update_entries!`: examined, nothing important hidden.**
   - JLD2's only write-side warning is the one for anonymous functions. The values written there are evaluated-stat lists, conversion datasets and metadata read back from the file, where reconstructions were already warned about on reading.
   - The header warnings (newer or foreign JLD2 version) still appear, because the read-mode open comes first.
   - `with_logger` is task-local, so other threads' logs are untouched.
   - It could be limited to files of version < 3.
6. **A mutated, inconsistent dataset no longer saves.** `_without_metadata` goes through the validating inner constructor, so an inconsistent `LSimData` (e.g. `push!(d.x[2], …)`) now fails to save with `DimensionMismatch`; 6faaec6 saved it (`wom.jl`). Probably an improvement. The cost is negligible.
7. **Recomputation now drops user metadata** (worth a line in the PR's breaking-change notes).
   - 0.4.4 carried user entries across every rewrite (checked in `origin/main_dev` `_write_sim_file`), and 6faaec6 across same-data recomputes.
   - Now a recomputed dataset (`force_overwrite`, `on_changed_sources = :recompute`) keeps only the pipeline's entries, and so do legacy files.
   - data.md and test line 581 document this.

## Verdict

278c925 fixes F1, F2, F3, F4, F6 and F7, most of F8, and old minors 1 and 2. The suite passes at `-t 1` and `-t 8`, and 10 of the new checks fail on 6faaec6's src.

Still open:
- **F5 isn't fixed.** Record updates on files with large metadata, including upgraded 0.4 files, still add a full copy per update. The new test can't detect it.
- **Two narrow regressions in the new legacy handling:**
  - an unreadable legacy entry aborts every rewrite, so post-processing fails on every run (Finding 2);
  - `_legacy_records!` alters 0.4 user entries (Finding 3).

All are low severity. None blocks the design, but Findings 1–3 are worth one more small commit.
